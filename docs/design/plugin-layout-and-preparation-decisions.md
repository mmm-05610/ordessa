# 插件分包与实施准备：讨论决策记录

日期：2026-09-27。状态：已确认方向的记录；不是实施授权，也不是完整实施规格。

本文件记录当前讨论结论，供后续设计与 Spec Kit 方案引用。此前调研中的目录草图与本文件冲突时，以本文件记录的后续裁定为准；正在执行的三个 Qoder 核心任务仍以各自已派发规格为准，不因本文件自动增加任务。

## 1. 总体原则

- Monorepo 根工作树保持 main；后续实现放独立 worktree。本次仅记录文档，不切分支、不提交、不合并、不推送。
- 核心层完成后，后续功能尽量落在 plugins，不能为了方便把业务重新塞进 Pacthold、Server 或 Workbench。
- 插件按业务独立性组织，不在 plugins 顶层统一拆 frontend/backend；一个业务域可以包含前后端包和各自注册入口。
- 插件族目录只是分类，不是额外的加载器、宿主或总服务；同族不意味着互相依赖或必须同时加载。
- 目录、发布包、运行时插件是不同边界。普通内部模块不必全部独立成插件。
- 判断边界以数据、副作用和生命周期所有权为依据，不以 UI 出现位置为依据。固定契约下尽量域内修改，契约演进时允许经审定的跨包变更。

## 2. 已确认的分包方向

以下树只表示本次确认的关系，不是完整现状树，也不要求创建所有占位目录。

```text
packages/
├── pacthold/                         # 中性执行/资源治理内核
├── workbench/                        # 按正在执行的核心方案归位
├── server-plugin-api/
└── desktop-platform/
    └── connections/                  # 通用连接设施；按已派发补充方案实施

apps/
├── server/                           # 通用宿主、传输、鉴权
└── desktop/                          # 桌面壳

plugins/
├── connectors/
│   ├── ordessa/                      # Ordessa 协议接入
│   └── acp/                          # ACP 协议客户端，不包含品牌配置策略
├── harness/                          # 逻辑域；是否放进 agent 族尚未定案
│   └── …                             # 原生适配器与配置应用留在域内
├── profile/                          # 配置集合、配置贡献、会话覆盖规则
├── agent-ui/                         # 可复用 Agent 展示组件
├── chat/                             # 业务接线和页面注册，不并入组件库
└── assets/                           # Harness 可配置/可装载能力插件族
    ├── model-provider/
    ├── skills/
    ├── prompts/
    ├── hooks/
    ├── mcp/
    ├── sandbox/                      # 仅 Harness 原生隔离能力的配置
    └── subagents/                    # 仅 Harness 原生子 Agent 定义和配置
```

- `assets` 在本项目中不是“静态文件目录”，而是可复用能力定义、内容、配置与接入的业务插件族。Model-provider 已同意归入此族。
- 不创建统管全部子插件的 AssetsService；没有真实共享需求，不先建 catalog 插件。
- 先前建议的 configuration/profile 与 configuration/model-provider 分组不采用：Profile 独立，Model-provider 归 assets。
- Workspace/Git、业务 Sessions、旧 agent 插件与 compat 的最终归位尚需结合核心交付核对；未被上树不表示删除或已经迁移。

## 3. Profile 与业务插件的关系

业务插件拥有完整业务，同时按需注册多个入口，不按页面拆散成不同业务插件。

例如 Skills 插件负责仓库、安装、内容、附件和版本，并可贡献：

- Settings 中的仓库/默认位置等管理区；
- Profile 中的启用集合和专用配置区；
- Chat 或其他界面的选择/浏览入口。

Model-provider 同理：管理供应商、模型、认证引用、设置表单与模型选择展示；向 Profile 注册默认配置，向 Chat 注册会话选择器。可用性依据 Harness 实际能力，不由表单猜测。

Profile 提供配置项 ID、结构/校验、默认值、版本迁移、编辑面与覆盖规则等扩展接缝，自己不内置 Skill、模型、MCP 等业务字段。具体 API 后续通过 Spec Kit 冻结，不把这份能力清单当作已存在接口。

数据关系：

- 插件保存业务实体，例如 Skill 内容和供应商记录。
- Profile 保存由插件定义和解释的配置片段，例如启用的 Skill 引用、模型选择。
- 专用 Skill 的正文/附件仍由 Skills 管理并关联 Profile，不把内容仓储塞进 Profile。
- 业务插件不依赖 Profile 才能独立工作；可选注册只有相关宿主存在时生效。
- 卸载配置面提供者：直接隐藏该区，不展示故障占位，保留已存配置。未知片段不得实际下发；重新加载后校验再使用。
- 会话临时修改不反写 Profile。Profile 更新只影响该会话未临时覆盖的字段。
- 显式切换 Profile 清除会话临时覆盖，不额外提示；本阶段不引入会话换 Harness。

## 4. 运行职责与 ACP 边界

- 不额外发起一次“把 ACP 全部抽出”的迁移。
- connectors/acp 负责协议消费；品牌差异、原生配置应用、必要的重启/resume 留在 Harness 适配层。
- 业务插件通过 Harness 公开能力应用配置，不直接覆写用户全局 Harness 配置目录。
- Harness 负责核实每个选项的支持范围、作用域、隔离方式与生效时机。可立即应用、下轮应用、需重启恢复、不支持必须如实区分。
- Profile 切换不得绕过强制安全限制；不支持原生隔离的能力不能伪装成已隔离。
- 原生 sandbox 配置不等于 Ordessa 的容器/远程执行环境；原生 subagents 不等于跨 Harness 派工与 Execution 编排。
- MCP 必须区分 Harness 原生托管与 Ordessa 托管，每个实例明确唯一运行/关闭所有者。
- Pacthold 管执行与资源生命周期，Server 管插件生命周期和传输；不把以上业务字段纳入核心。

## 5. Agent UI 的裁定

- 名称采用 `agent-ui`，优先复用 ZCode 展示组件。
- 可复用候选：消息/Markdown/附件、思考、工具调用/结果、审批卡、输入框布局、配置继承/覆盖/生效状态。
- 不引入 ZCode 的业务 store、RPC、服务总接口来支撑组件；不能假定展示文件没有隐含依赖，移植前逐项核查。
- 通用按钮、表单、Dialog、Popover、焦点与浮层机制优先复用现有平台能力，不再搭一套。
- Agent UI 接收数据与回调，不自行连接 Server、创建会话、保存配置或执行审批；业务插件负责接线。
- Chat 保留会话选择、发送、订阅、草稿、Workbench 页面与导航注册；纯展示部分可以提取为 ConversationView 等组件。
- 后续讨论已确认组件替换需求：agent-ui 分轻量领域 API 与默认实现插件；默认插件通过通用 UI 服务登记实现，业务消费者只导入 API，不直接依赖其 src。具体见 [组件契约设计](agent-ui-contracts/README.md)。这取代最初“先做直接 import 的共享组件包”的方案。

依赖方向：业务消费者与 Agent UI 实现都依赖领域轻量 API 和通用 UI 服务；核心不反向导入领域 API。默认组件内部仍消费平台基础 UI，不反向依赖业务服务。

## 6. 暂不预先独立成包的候选

- permissions：工具/审批规则，与 sandbox 不同；是否独立待明确业务规模。
- context：压缩、裁剪、保留参数；先判断是否只需一个小配置贡献。
- memory：原生记忆配置与 Ordessa 记忆服务分开核对，不提前让两处拥有同一数据。
- extensions：管理 Harness 原生扩展包，不与 Ordessa 插件宿主混淆。
- prompts 可先容纳指令片段、模板和输出风格，是否拆开由实际需求决定。

这些是调研候选，不是今晚自动必须交付的新增插件。

## 7. 复用纪律：先定模块，再派实施

禁止只写“自行寻找开源项目复用”。每个模块在派发前需完成下列信息：

| 项 | 必须确定的内容 |
|---|---|
| 所有权 | 做什么、不做什么；数据、副作用、资源归谁 |
| 接口 | 输入/输出、错误、事件、缺席/卸载行为 |
| 来源 | 仓库、固定 SHA、具体文件或包接口、许可证及必要声明 |
| 方式 | 直接依赖 / 源码移植 / 借鉴设计 / 自行实现，四者分清 |
| 适配 | 保留内容、必须剥离的上游依赖、自己的接线代码 |
| 验收 | 正例、反例、集成证据、未测范围 |

常见裁定：思考与工具卡优先核对 ZCode；浮层和通用表单优先使用现有平台；原生配置应用优先复用适配器；Profile 特有覆盖语义按本项目规格实现，不能强套语义不同的上游模型。

实施退路也须事先定义：首选 → 限定适配 → 已核对备选 → 记录局部阻塞并继续独立模块。不能悄悄重写、新增框架、扩大宿主接口或复制服务来绕过阻塞。小阻塞不等于整晚停止，但未完成项不能计为完成。

## 8. 已确认的准备顺序

1. **Agent UI**：逐组件确定 ZCode 来源、依赖、许可、适配边界和业务可消费接口。
2. **Profile + Model-provider + Skills**：第一组端到端样板；冻结 Settings、Profile 贡献与 Harness 应用的接缝。
3. **MCP、Hooks、Prompts、原生 Subagents、原生 Sandbox**：复用样板的接入方式，但分别核对 Harness 差异。
4. **三个 Qoder 核心任务完成并验收后**：与实际核心导出接口对照，修订/冻结最终契约，划分不争抢文件的 worktree，再派无人值守实施。

现在可以做只读研究与设计；不改变进行中的任务、不提前假定核心 API 已交付。今晚交付范围按明确能力和验收项确定，不按“所有目录都填满”确定。
