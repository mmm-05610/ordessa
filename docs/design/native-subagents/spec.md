# Feature specification

## 用户故事

### US1 / P1：保存并版本化一种角色定义

用户建立“只读代码审阅者”，写清名称、调用描述、角色指令及期望工具边界，保存不可变修订。Given 旧修订已被会话引用，When 编辑发布新修订，Then 历史修订仍可解析，已有固定引用不暗中变化；导入未经信任的定义不执行其中脚本/命令。

### US2 / P1：按范围启用而不混淆策略

用户让项目 A 的 Claude Profile 启用定义，但项目 B 和 Codex Profile 不受影响。保存、用户全局默认、项目默认、Profile 选择分离；项目身份由 Workspace 服务端验证。未知原生版本/缺适配器时，内容仍可编辑，应用前类型化拒绝。

### US3 / P1：不能由定义提升权限

Given 定义要求 `Bash`、某 MCP 服务或宽松审批，When 它超过当前用户、项目或会话允许的能力，Then 在装载/运行前拒绝或收窄为显式且经验证的有效能力，绝不因为定义文案、原生 `permissionMode` 或插件来源而放宽强制边界。为防伪安全感，首版采取**拒绝**超界/无法验证的配置，而非静默收窄后声称原样生效。

### US4 / P1：下一次提交生效且并发不串

Given A 正在输出、B 在另一个会话有另一版本，When 用户调整 A 的 Profile 选择，Then A 当前输出不变；下一次输入前按固定快照应用，B 的实例与用户 HOME/项目原生定义字节不变。恢复仍是同一 native session；不能以 `session/new` 代替。

### US5 / P2：观察原生定义并诊断来源

用户看到当前 Harness 自己发现的项目/用户定义与 Ordessa 受管定义分列；未受管项只读。原生同名冲突时不靠加载顺序获胜。原生机制不能屏蔽旧项目定义时，不显示“已禁用”；请求确切有效集合则拒绝隔离不成立。

### US6 / P2：从 Chat 找到可用角色

Chat 只对已证明确实可调用的目标展示“使用此子代理”；点击仍受运行权限/会话提交闸门约束。无法受控显式调用的定义仅供详情浏览，不通过拼普通用户消息假装创建子代理。子代理运行和回传不是本插件的服务实现。

## 功能需求

| ID | 要求 |
| --- | --- |
| FR01 | 定义库存：稳定 ID、用途描述、角色正文、不可变修订、来源/摘要、归档与安全预览 |
| FR02 | 内容归属公共/项目专用/Profile 专用，与启用分配分离；编辑不自动更新固定分配 |
| FR03 | 用户全局、项目、Profile、会话覆盖的确定性解析；Harness 绑定不混品牌 |
| FR04 | 每次提交冻结定义修订、项目/Profile/会话/adapter generation；失效在副作用前拒绝 |
| FR05 | 定义引用模型、工具、MCP、Skills、权限/隔离/预算等**仅作为声明**；引用由各属主授权解析，不复制秘密 |
| FR06 | 任何声明不得提升强制权限；未知/无法映射的安全字段 fail closed，不丢字段假装成功 |
| FR07 | 各品牌/版本明确区分原生、extension-backed、unsupported、unknown 及装载/调用证据 |
| FR08 | Harness adapter 负责配置 intent 编译/验证；业务服务不写原生文件、spawn 子代理或调用模型 |
| FR09 | Ordessa 受管定义只写实例私有 generation，移除/切换有完整 reset；不得覆盖用户或项目原生文件 |
| FR10 | 同名、发现层、角色描述长度和原生保留名冲突在应用前诊断；不能 last-wins |
| FR11 | Settings、Profile 编辑器和可选 Chat 入口分别经公开贡献注册；缺贡献不崩其他域 |
| FR12 | 不能复用旧 Profile 的 `run_subagent` 授权表作为本插件的定义仓或建第二套派工系统 |
| FR13 | 迁移旧定义仅在可证据映射时执行，旧授权边/运行历史不默迁；ID、格式、回滚有表 |
| FR14 | 导入只复制经批准内容；无递归 include、shell 模板、自动远程下载或秘密明文日志 |
| FR15 | 启用/移除/版本更新需要受控原生加载与可调用性证据；材料化文件存在不等于加载/调用 |
| FR16 | 产品/包边界、失败 ID、服务缺席/卸载、用户数据恢复有可复核验证 |

## 非目标和成功条件

不建立跨 Harness 团队、派工单、通信总线、审批服务、执行恢复、工作树编排或多代理 Workflow。子代理定义可以描述工作方式，但运行策略由所属 Harness/将来的通用设施管理。资源引用独立保存，未部署的 MCP/Skill 不因定义提及而自动安装；普通定义不授予工具。

成功不是“三个品牌表单都能保存”，而是当前 pin 的能力矩阵、实例隔离、下一次提交装载和至少一个真实受控调用入口的 L3 证据。Claude/Codex 为原生目标；Pi 的目标若采用扩展则需明示 extension-backed 并取得该扩展审查/接线证据，否则 Pi 保持不可提供，本包不可报告三品牌全绿。真实模型调用不在本设计授权范围。
