# Agent UI 组件契约总览

状态：设计稿第二版。替代第一版“只开放四个接口”的范围。本文定义组件家族、主要输入、动作与组合方式；具体 TypeScript 字段由领域契约落实。没有实现的组件不得注册成功空壳。

## 1. 目标与范围

业务插件应当可以组合现成组件，完成 Agent 对话、配置、资源管理和运行观察界面。它负责业务数据和操作；Agent UI 负责一致的呈现和交互。相同组件能出现在主页面、侧栏、底部面板或浮层中，打开到哪个位置由 Workbench 与业务插件决定。

界面分为三个层次：

| 层 | 例子 | 归属 |
| --- | --- | --- |
| 基础控件与布局设施 | Button、Input、Select、Dialog、Popover、主题、焦点 | 平台现有 UI 能力 |
| Agent 语义组件 | 工具记录、审批、消息输入、配置继承状态、运行摘要 | Agent UI 默认实现和可替换接口 |
| 业务页面与注册 | Chat、Profile 设置、供应商管理、Skill 仓库 | 各业务插件 |

“Agent UI 提供通用配置区”不意味着它保存配置；“提供进度组件”不意味着它定义工作制度、任务调度或工单格式。

## 2. 完整组件目录

共 12 个独立可消费接口，分为五组。每组是模块组织，不是必须共同安装的插件。产品只为实际使用的接口配置提供者。

| 组 | 接口 / key 后缀 | 主要用途 | 主要消费者 |
| --- | --- | --- | --- |
| 对话 | ConversationView / conversation | 消息、思考、工具、交互和历史组成的内容流 | Chat、运行详情 |
| 对话 | Composer / composer | 输入、附件、命令建议与工具栏 | Chat、派工入口 |
| 执行交互 | ToolActivity / tool-activity | 单次或一组工具调用、参数、输出、状态 | 对话、执行详情、审计 |
| 执行交互 | ApprovalView / approval | 审批内容、选项、提交与结果状态 | Chat、审批面板 |
| 执行交互 | QuestionView / question | Agent 向用户提出的结构化问题 | Chat、工作面板 |
| 选择与配置 | EntitySelector / entity-selector | 单选/多选、分组、搜索、可用性说明 | 模型、Profile、Skill、MCP 等选择 |
| 选择与配置 | ConfigurationSection / configuration-section | 配置区、字段、校验、保存与应用入口 | Settings、Profile、局部会话配置 |
| 选择与配置 | ConfigurationState / configuration-state | 来源、临时覆盖、生效时机和失败原因 | 配置字段旁、选择器旁 |
| 内容审阅 | ResourcePreview / resource-preview | Markdown、文本、附件、资源元信息与版本说明 | Skills、Prompts、附件详情 |
| 内容审阅 | ChangeReview / change-review | 文件/配置变更列表、diff、审阅操作 | 工具结果、配置预览、Git |
| 工作观察 | WorkProgress / work-progress | 计划项、任务项、检查项的分组进度 | Chat、未来工作系统 |
| 工作观察 | RunSummary / run-summary | 当前运行状态、主体、用量、可用操作 | 会话标题、侧栏、运行详情 |

所有 key 都在 `ordessa.agent-ui.*` 名字空间，初始 major=1。同一实现可提供多项，替换插件也可只提供一项。

## 3. 各组件的接口范围

### 3.1 ConversationView

输入：会话显示 ID、消息快照、消息内容块、历史完整度、当前运行/连接状态。支持用户消息、Agent 消息、通知、思考、工具、审批、问题、进度、资源和变更引用。时间、作者、模型标签按需显示，展示标签由业务提供。

输出：请求较早历史、打开引用/附件、复制或其他由消费者明确提供的消息动作。重新生成、编辑重发、分支等作为可选业务动作；组件不假定每个 Harness 都支持。

组合位置：顶部说明、空态、消息附加信息、消息动作区、内容块渲染入口、底部补充区。内容块没有对应实现时显示类型和简要文本，并禁用该块操作，不能静默丢失。

默认交互：流式内容更新；阅读历史时不抢滚动；新内容提示；内容折叠；显式加载历史；消息/内容块使用稳定 ID。列表虚拟化是实现选择，不能要求消费者使用某个状态库。

### 3.2 Composer

输入：受控文本、草稿 ID、附件、发送/停止可用性、建议列表、辅助说明，以及顶部/底部工具区。provider/model、Profile 等选择器通过这些位置组合。

输出：文本变化、提交、停止、选择/移除附件、选中建议项。文件拖入和粘贴可以提供可选回调，由业务接收文件并处理权限、大小限制与上传；组件不自行持久化或发送。剪贴板读写需要显式用户动作。

建议项能表达 /命令、@引用等，匹配/加载由业务提供。组件处理键盘选择、输入法和菜单可访问性，不能根据斜杠命令名字执行原生功能。发送成功后是否清空文本由业务更新 props。

### 3.3 ToolActivity

输入：单个或多个工具记录、标题、类型标签、执行状态、参数摘要/全文、输出片段、错误、时间，以及可用操作。输出可流式追加；长输出需明确是否截断、是否还能加载。

输出：打开完整输出、复制、打开附件/路径、展开关联变更。取消/重试只在业务显式给出动作时出现。状态包括 pending/running/succeeded/failed/cancelled/unknown，不能靠“收到了输出”推断成功。

工具记录可引用 ResourcePreview/ChangeReview；文本和 JSON 展示有内置基础表达，特殊结果通过消费者传入的渲染入口扩展。

### 3.4 ApprovalView

输入：审批 ID、操作说明、风险/影响提示、业务提供的选项与禁用原因、提交和最终状态。可呈现待审批及历史记录两种布局。

输出：选择某个选项。选项 ID 是不透明值；“一次/本次会话/长期”等范围全部由业务解释。组件不得将文字中的“允许”推成权限操作。

审批已失效、状态未知、正在提交时不能重复提交。需要对比的操作内容可由 ChangeReview 或描述区呈现。

### 3.5 QuestionView

输入：问题集合、说明、每题输入种类、选项、是否允许自由文本、是否必答、受控答案、验证提示及提交状态。输入种类支持单选、多选、短文本、长文本；更复杂的编辑器由消费者传入。

输出：答案变化、提交、跳过/取消（仅显式可用时）。多题可以一起回答，不强制固定问卷流程。组件不替用户自动选择建议答案，也不将未回答视为同意。

审批与提问分开：审批改变授权，提问收集信息；不能用同一个“确认”动作偷换语义。

### 3.6 EntitySelector

输入：候选项 ID、名称、说明、图标、分组、标签、可用/禁用原因；受控选中 ID；单选或多选；加载、空、错误状态；可选搜索文本和分页信息。

输出：选择变化、搜索请求、加载更多、刷新、打开管理页。它可以放进输入框底部或设置页；紧凑和展开布局是呈现模式。

不内置 harness/provider/model 三级树。model-provider 可以把候选模型按 provider 分组；联动的两个选择器由业务组合。自动预选、选择持久化、失效选项的回退都由业务决定。暂时不在当前页的已选项仍可通过 selectedItems 显示，不能自行清空。

### 3.7 ConfigurationSection

输入：标题、说明、分组字段、受控值、字段级错误、只读/禁用原因、是否有未保存修改、保存/应用状态，以及按钮动作。

提供常见字段表达：文本、多行、数字、开关、单选、多选、资源引用；嵌套组只负责布局。自定义字段以消费者提供的可信 React 内容显示。字段可附 ConfigurationState，说明 Profile 继承和会话覆盖。

输出：字段变化、保存、应用、撤销局部编辑、重置覆盖。哪些操作存在由业务声明；“保存成功”不自动等于“已经应用到正在运行的 Harness”。字段校验和配置迁移归业务，控件只承担基本输入约束和错误展示。

凭据字段传入引用和脱敏描述，录入/替换动作交给凭据业务界面；保存过的密钥不应在普通配置值中往返。设置项提供者缺席时由业务不再贡献该字段，旧配置数据保留。

### 3.8 ConfigurationState

输入：来源（默认/Profile/会话）、生效状态、必要说明、可用重置/应用动作。来源与生效状态独立；支持“来自 Profile，但下一轮生效”和“会话覆盖，应用失败”。

这是可单独使用的紧凑组件，也可置于 ConfigurationSection/EntitySelector 旁边。其布局不能要求外层一定是 Profile 页面。

### 3.9 ResourcePreview

输入：资源显示 ID、名称、类型、内容/预览数据、来源说明、版本标签、加载状态、是否截断，以及消费者提供的操作。

显示文本/Markdown/代码/已允许的图片与附件信息。Skill 正文、Prompt、MCP 配置说明等都能使用。完整版本管理、安装、同步、启用关系仍由资产插件决定。

输出：打开资源、打开外部编辑器、复制、加载完整内容，以及业务声明的安装/启用等操作。原始 HTML、脚本和网络内容不能因“预览”直接执行；外部资源读取归消费者。

### 3.10 ChangeReview

输入：变更集合、文件/配置项标签、前后版本说明、文本 diff 或结构化差异、部分/完整状态、选中项和操作可用性。

输出：选择变更、打开文件、展开、应用/拒绝选定变更（只有消费者提供此能力时）。组件不运行 git、不写文件、不决定补丁是否仍可应用。二进制/过大/不支持的变更显示明确摘要。

它既可出现在工具结果，也可用于配置应用前的预览；路径是显示内容，操作通过不透明变更 ID 交回业务。

### 3.11 WorkProgress

输入：条目 ID、标题、说明、状态、可选父项/分组、负责人标签、已有进度和证据引用。状态采用 todo/active/blocked/done/failed/cancelled/unknown 的展示分类，业务可补充原始状态说明。

输出：查看条目、展开分组、打开证据，以及显式提供的业务动作。并列/树状均可，v1 不处理循环图；适配数据需保证树结构合法。

不规定工单完整字段、固定执行顺序、DAG、重试次数或替补策略。Skill 需要记录的新业务字段放在其服务中，组件可显示传入摘要/详情插槽。某条显示 done 不代表整个 Execution 已结束。

### 3.12 RunSummary

输入：运行显示 ID、当前阶段、连接状态、Agent/模型等显示标签、时间、用量条目、可用操作及解释。用量项是名称、值、单位和是否估算，不假定所有 Harness 都有费用/token 数据。

输出：打开详情、请求停止、恢复或其他业务动作。恢复是否新建 Execution 由业务处理；组件不能把终态执行改回 running。连接失效和运行未知分别显示，数据缺席不显示为零。

可用于标题栏、状态栏、卡片和详情顶部；紧凑布局只压缩信息，不改变状态含义。

## 4. 所有接口共用的表达

这部分放 Agent UI 的领域 API，平台组件注册服务只保留泛型 P，不知道这些类型。

| 共用表达 | 规则 |
| --- | --- |
| 身份 | 稳定 opaque ID；消费者负责 Server/Harness/native ID 的去重和映射 |
| 动作 | ID、label、可用性/原因、pending、执行回调；已接纳不等于成功，副作用回调经过平台 guard |
| 内容加载 | not-loaded/loading/ready/partial/error；空集合是 ready 的合法结果，不能与未加载混淆 |
| 错误 | 可展示说明、可选显式重试；不传完整堆栈/凭据；组件报错与业务操作失败分别显示 |
| 分页 | hasMore 与显式 loadMore；无隐式轮询，无自动重复提交 |
| 受控状态 | 数据、选择、输入、业务展开目标由消费者持有；临时 hover/折叠等可在组件内部 |
| 布局 | compact/comfortable，适应父容器；不自建窗口或假定全屏，不以布局尺寸推断业务权限 |
| 能力 | 通过可选动作、明确禁用原因和可选数据表达；没有“所有 Harness 都支持”的默认值 |
| 本地化 | 平台 locale/theme/direction；业务名称与原文不擅自翻译；系统控件文案使用统一词表 |
| 辅助访问 | ariaLabel、键盘导航、可见焦点、状态文本；颜色不能是唯一状态依据 |

共用动作只负责呈现和调用，确认弹窗规则由动作所有者通过平台浮层实现。组件不暗中增加二次确认，也不能绕过业务要求的确认。

## 5. 组件怎样组合与替换

1. 业务插件向通用 UI 服务 bind 所需接口。
2. 业务把自己的状态转换为对应展示数据。
3. 业务使用 ComponentOutlet 显示该接口，并传入所需的子内容渲染函数。
4. 复杂组件需要嵌入 ToolActivity/Approval 等时，由消费者或领域 API 的轻量组合 helper 把绑定连接好；默认实现不自行访问任意业务服务。

组合 helper 可以封装“内容 kind → 对应 Outlet”映射，减少 Chat 的重复接线。它只调用传入的 bindings 和动作，不持有业务 store、不创建隐藏绑定、不登记提供者。依赖方向始终为 helper → 领域 API + 通用消费工具。

例如产品只更换 ToolActivity 提供者，Conversation 里的工具块和执行详情里的工具块都通过同一接口得到新外观；单独使用 ApprovalView 不要求加载 Conversation。

缺子组件时：审批/问题等交互块只读展示描述，操作禁用；资源/工具块保留文本摘要；绝不静默丢失内容。如果该位置是产品承诺的必需能力，装配诊断同时报告缺提供者。

## 6. 布局位置与组件接口的区别

Workbench 负责页面、侧栏、底部面板、设置区和浮层的位置。Chat/Profile 的贡献 API 负责谁能往该业务页面增加内容。Agent UI 负责放到这些位置上的具体组件。

例如 model-provider 向 Chat 注册一个输入区工具项，再通过 EntitySelector 显示；向 Profile 注册配置项，再通过 ConfigurationSection 显示。它不向核心注册“model-provider 业务”，也不让核心识别模型。

## 7. 分包与落实顺序

```text
plugins/agent-ui/
├── api/
│   ├── common/             # 动作、显示数据、受控状态和布局约定
│   ├── conversation/       # Conversation / Composer
│   ├── interaction/        # ToolActivity / Approval / Question
│   ├── configuration/      # EntitySelector / Section / State
│   ├── review/             # ResourcePreview / ChangeReview
│   ├── work/               # WorkProgress / RunSummary
│   └── composition/        # 可选的轻量内容渲染接线 helper
├── src/                    # 按相同家族组织默认实现
├── tests/
├── examples/               # 同一组数据用于视觉验收
└── THIRD_PARTY_NOTICES.md
```

契约按完整 12 项设计。实现优先：

1. 对话/工具/审批/输入，服务现有 Chat。
2. 选择/配置/资源预览，服务 Profile、model-provider、Skills。
3. 问题/变更审阅/工作进度/运行摘要，服务后续原型。

优先级只决定排期，不改变插件边界。API-only 目录可以先存在；未实现能力不得加入产品必需清单，也不得在交付中写成已经可用。新增这些领域接口不应再要求 C7 平台修改。

## 8. 后续类型冻结的边界

本次先确定所有公开组件、数据所有权、动作与组合方式。字段命名、图标集、是否使用某个列表虚拟化库等在逐模块复用审计时确定；执行者不得借这些内部选择改变生命周期、权限或状态语义。

现有 contracts/agent-ui.md 的四项 TS 草图仍作为起点，但本总览在能力覆盖上优先；正式实施前把其中四项及新增八项一起整理为可编译、互相一致的领域 API。核心 Qoder 只消费通用 C7 契约，完全不需要在宿主内预先列出这 12 个接口。
