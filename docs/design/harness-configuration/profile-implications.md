# 对 Profile 的影响：不增加用户操作复杂度

本文是研究推导；保留 profile-v2 中已确认的产品语义，不取代其实施包。

## 不变的用户体验

- Profile 属于一个 Harness；现有会话不换 Harness。
- 会话中像切模型一样选择 Profile。正在输出时不打断；下一次用户提交前应用。
- 会话临时修改不反写全局 Profile；未覆盖字段跟随 Profile 的后续修改。
- 主动选择另一个 Profile 后，成功应用的新配置不保留旧临时覆盖；失败/未知不能谎称已完成。
- UI 不新增“当前/待生效/有修改”常驻状态组。真正失败时必须说明原因，不能隐藏失败。
- 配置贡献者卸载后隐藏对应编辑项，保留数据。

## 后台必须多做的工作

每次应用的目标不是“把所有文件覆盖一遍”，而是生成这个会话的有效配置差异：

1. 读取选定 Profile 与本会话覆盖、引用资源的确定版本。
2. 按真实 Harness 版本、运行模式、组织约束校验所有差异。
3. 将每项差异归入请求参数、原生 API、reload 或进程替换路径；未证实的路径不能自动成功。
4. 在下一条用户输入交给模型之前完成必要应用；任何失败不得把消息发给半配置的 agent。
5. 保留旧有效配置与会话身份，避免重复发送。需要重启时恢复原会话；新 execution 不等于新 conversation。
6. 确认生效后记录内部 revision 与证据；不是要求用户面对一套配置事务界面。

这不是要求 Profile 理解所有原生文件。业务插件解释自己的配置，Harness 适配层负责原生应用能力和限制；Profile 负责预设/覆盖关系。工作内核只做通用生命周期与资源治理。

## 配置字段的记录模板（研究/契约输入，不是运行时新 API）

| 字段 | 必填含义 |
| --- | --- |
| capabilityId / owner | 稳定语义 ID 与业务所有者；不以原生文件路径作为唯一身份 |
| harness / version / surface | 具体版本及 CLI、RPC、ACP、SDK、gateway 等入口 |
| purpose / mechanism | classification.md 中的两条分类轴 |
| nativeBinding | 原生键/文件/命令/API；不包含实际 secret 值 |
| schema / default / unset | 类型、取值、缺省、删除与继承的区别 |
| precedence / merge | 原生层级和合并算法；额外扫描来源 |
| profileEligibility | 可保存、只可引用、管理设置、强制约束、运行状态、未确定 |
| applyMode / isolation | 生效时点、影响范围、是否专用实例、共享副作用 |
| verification | 有效值查询/行为探针/官方保证；仅写盘必须标不足 |
| failure / rollback | 不支持、依赖缺失、拒绝、未知结果、恢复条件 |
| source | 官方 URL、查询时间、版本/commit、待核实项 |

## 必须钉住的反例

1. 两个同 Harness 会话使用不同供应商/Skill/MCP；改 A 不影响 B，也不改用户全局文件。
2. 同字段全局 Profile 与会话均修改：仅会话值优先；其他字段仍跟随全局。
3. 选择新 Profile 清覆盖，但应用失败不得丢弃仍有效的旧状态。
4. Profile 开启权限被管理员策略禁止：拒绝或诚实说明受限，不通过降级伪装成成功。
5. Skill 含不支持的安全 frontmatter：不可静默剥除后宣告兼容。
6. 一个值被原生项目配置覆盖：回读/行为证据必须暴露差异。
7. 切换需重启，但原会话无法恢复：不自动创建新 conversation 代替。
8. Hook/MCP 不可用：区分可选缺席与必须满足的安全条件；后者不能 fail open。
9. 原生 `/model` 会保存默认值：Ordessa 会话切换不得意外触发全局保存。
10. provider 卸载：UI 隐藏、数据保留；再次应用缺失能力不能假装已应用。

## 复用方向（候选，不是已批准复制清单）

| 复用对象 | 优先参考 | 直接复用边界 |
| --- | --- | --- |
| 原生配置结构与校验 | 官方 Schema；dsh 生成目录与 runtime schema；Codex 配置参考 | pin 版本、检查许可证；schema 不自动带来生效机制 |
| Skill 包结构 | Agent Skills 标准 + 每家 loader 行为 | 共用资源管理，保留各家字段/发现差异 |
| 原生配置应用 | 官方 RPC/SDK/ACP/会话接口 | 不用模拟 TUI 键盘当稳定生产接口；不把客户端 UI 可选项当协议支持 |
| 设置表单/资源选择 | 现有平台 ui、Profile 扩展面 | 不把原生 TUI 组件移进平台内核 |
| Provider 管理 UX | 后续单独评估 cc-switch 等项目 | 它管理全局配置的写入策略不能直接用于会话隔离 |
| Skills/MCP/Hooks 编辑 | 后续按业务插件挑选源模块 | 本轮尚未完成每个模块的代码级复用/许可证审查，不得说“可直接搬” |

建议接下来先审六种处理机制与 Profile 边界，再按“内容资源 → 服务绑定 → 强制策略/执行扩展”分别形成实施规格。无需先讨论数百个原生字段的表单细节。
