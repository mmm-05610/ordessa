# Ordessa：面向软件工程的 Harness

## 1. 产品定位与这份文档的作用

Ordessa 的新方向是一个面向软件工程的 Harness：接入不同品牌的 Harness，将它们作为实际工作的 Agent 节点，在其上管理开发工作的讨论、工程材料、审核、交接与核验。

产品不重新实现模型推理循环、工具调用循环或各家 Harness 的内部功能。它依赖 agent-node 提供可管理、可使用的工作节点，并利用可加载的工程工作流和文档标准，让这些节点参与同一套可追溯的软件工程工作。

这里的“工程工作流”指一次开发工作从想法、设计变更到实施与核验的推进方式，不是替代 Harness 内部的推理循环。Ordessa 管理工作之间的边界、材料和许可；Harness 管理自己内部怎样思考和执行。

这份文档固定本轮产品方向，展开其责任和使用方式。它不是已经落地的系统说明，也不是实施任务包。用户明确提出的方向与 Agent 的设计建议分别标记；保存文档不表示所有建议已经获准实施。

本文不改变现有代码或正式 DID，不授权移动 Decision 模块、重启服务、调用真实模型或派实施任务。当前各工作树能力不能仅凭历史讨论判定已完成。

## 2. 为什么收窄方向

此前的目标是提供一个完全开放、可插拔、容纳 Agent 和各种外部能力的工作环境。这一目标可以覆盖很多场景，但它容易迫使核心先为尚不明确的业务提供抽象，增加组织和理解成本。

本轮不再以“能承载一切”衡量产品。开放性保留，但服务于明确的软件工程用途：

- 同一个开发者可以使用多个 Agent，不必逐个阅读全部聊天和工程材料。
- 想法变成实施要求时，重要选择有出处，不被 Agent 悄悄补齐。
- 实施 Agent 获得足够明确的材料，不必越过自己的任务层级补做产品和架构设计。
- 用户能了解准备改变什么、做到哪里、偏离在哪里、什么事情需要自己决定。
- 实现结果能够和批准的目标对应起来，而不是以“做完了一批文件”代替交付。

这是方向收敛，不是要求当场删除通用基础设施。现有能力是否保留，应由其是否支撑上述使用方式以及实际源码依赖决定，另行设计迁移。

## 3. 产品要提供的完整体验

### 3.1 用户提出的是工作意图，不是完整工程规格

用户可以提出“统一会话管理”“这个状态只能有一份”“把配置模块从插件迁到核心”等意图。系统不能因为用户要求出包，就把尚未讨论的行为、恢复规则和迁移选择默认填完。

主 Agent 帮助讨论目标与重要取舍；系统保存讨论成果，同时把仍然缺少依据的选择保留为未决项。普通实现细节可以在明确授权内由 Agent 选择，不要求用户逐项设计函数和算法。

### 3.2 用户不通读材料，但仍参与重要决定

产品默认用户不会逐页阅读 DID 或实施包。重要变化必须以可理解的摘要出现在工作会话中：准备改变什么、保留什么、删除什么承诺、有哪些取舍和风险、哪些事情尚未确定。

发送摘要不等于用户读过，更不等于用户明确同意。用户可以明确接受；也可以预先授权特定范围内“告知且没有否认则暂准”的规则。后者必须有范围和可核验条件，不能由系统临时猜一个等待时间。

### 3.3 Agent 使用工程材料执行，用户观察工作状态

实施者拿到按批准设计展开的任务材料。用户观察的是目标、已完成和未完成范围、阻塞、待决定事项与验证证据，而不是被迫自己拼接每个 Agent 的输出。

聊天记录可以成为证据来源，但不应是掌握进度的唯一入口。文档数量、Token 消耗、运行时长和任务勾选数量都不能独自代表工作完成。

## 4. 三类工程材料与一类操作方法

### 4.1 决定与依据记录：为什么允许这样规定

保存用户明确决定、授权范围、有效项目约定和已有批准内容。事实观察与参考项目可以帮助设计，但不能自动授权新的产品行为。

记录必须能离开原聊天被理解：说明对象、场景、范围、决定内容和出处。补全的是上下文，不是补做决定。用户可以修改自己的选择；后续材料应能定位受影响的规定。

### 4.2 长期 DID：这个软件应该是什么

按选定 Data Item Description 标准组织的需求、设计、接口及必要的数据设计文档，作为持续维护的工程基线。并非每个项目必须使用所有文档类型，也不意味着某一份标准能消除全部歧义。

每次工作改变相关内容，形成明确的文档修订。实质性增加、修改和删除都有依据、有影响说明、有审核及接受记录。实现状态与目标设计分开表达，不把尚未实现的目标写成已经验证的产品事实。

### 4.3 本次实施包：怎样落实这次批准变更

使用 Spec Kit 的 spec、plan、tasks 分工及相应的契约、组件设计、实施切片与验收材料。这里只借用文档格式和约束，不要求运行 Spec Kit 原生工作流。

实施包是 DID 本次变更的执行视图，不是第二份长期设计权威。它指明改哪里、增删改什么、依赖什么、保留什么、怎样核验，以及缺资源时哪些工作能继续。

若转换中发现重要设计缺口，应回到 DID 变更环节，不能在 tasks 中另起一套设计。任务完成后的记录可以归档，但长期 DID 继续维护。

### 4.4 Skill：Agent 如何完成某个操作

Skill 提供记录、起草、审核、转换等操作指引。它不是批准依据，不因被加载就取得写入或实施权限，也不能单凭提示词成为不可绕过的门禁。

工程工作流安排这些操作什么时候发生；标准定义材料需要达到什么要求；Skill 帮助 Agent 完成具体操作。三者关联，但不合并为一个拥有全部状态和权限的对象。

## 5. 从想法到核验的工作闭环

下图表达工作阶段及问题返回的位置，不表达源码依赖或进程通信。

```text
讨论意图与重要取舍
        │
        ▼
记录决定、授权、假设与未决项
        │
        ▼
提出 DID 增删改及影响分析 ◄────────────┐
        │                             │
        ▼                             │
审核依据、工程质量、用户摘要 ──问题───┘
        │
        ▼
会话告知 → 明确接受 / 按授权策略暂准
        │
        ▼
受控更新 DID，建立目标基线
        │
        ▼
生成实施包 ◄────转换问题──── 实施包审核
        │                         │
        └─────────────────────────┘
                                  │
                         有相应实施授权
                                  ▼
                         agent-node 实施
                                  │
                                  ▼
                         对照目标核验结果
                                  │
                     问题反馈到实现、设计或方法
```

### 5.1 讨论与留档

讨论得到明确决定及授权；未确定的选择保持未决。记录应区分明确决定、明确授权、Agent 解释和开放问题，不能因为用户没有逐句纠正记录就把全部解释当确认。

### 5.2 DID 变更提案

固定原基线、目标范围与依据版本。提案包括变更原因和影响、精确增删改、每项规定的依据，以及受影响但要保持的约束。小变更可以合并文件，不机械制造完整空目录。

### 5.3 系统审核

审核承担三种不同问题：依据是否在含义上支持规定；内容是否满足选定工程标准；会话摘要是否忠实表达重要变化。引用正确的编号不代表新增的全部行为都有依据，章节齐全也不代表内容足够明确。

审核问题应有目标位置、具体影响和返回责任。表达不足交作者修订；事实不明先调查；缺重要决定再问用户；冲突不能只挑选有利材料绕过去。

### 5.4 告知与接受

系统自审后发送摘要，绑定提案版本。接受记录区分明确批准和策略支持的暂准。审核通过只说明没有发现适用范围内的阻塞，不自动产生用户授权。

实质性修订后，旧审核、告知及批准不能自动覆盖新内容。并非所有变化都要求全量重审，但需先判断和记录影响。

### 5.5 正式更新与转换

取得相应写入权限后，核对基线、精确补丁、审核与接受范围，更新 DID 并回读记录结果。版本冲突必须合并和复审，不能仅刷新版本号覆盖。

随后从这次目标变更形成实施包，核对变更到任务、任务到验收的正向映射，以及每条任务到批准规定或授权自由的反向映射。

### 5.6 实施与核验

实施授权独立于文档接受。实施节点在允许范围内工作，遇到重要设计缺口返回，不以隐藏兼容链或自行补规则撑出完成假象。独立、已明确的范围可以继续，不因一个问题冻结所有工作。

核验结果必须区分已完成、失败、阻塞和未验证。真实产品行为、真实 Harness、替身测试和离线验证不能混称同一层证据。

## 6. 目标责任划分

本节是 Agent 对已确认方向的设计展开，不是已批准的包目录或接口契约。

### 6.1 agent-node：实际工作单元

提供已有设计中的可使用与可管理入口，把不同品牌 Harness 作为工作节点交给上层。内部循环、原生能力和配置变更的具体处理由对应实现负责。

工程流程可以请求节点起草、审核或实施，但不应为了每个原生功能再实现一遍 Harness。不同 Harness 的能力差异须明确暴露，不能以统一接口暗示全部能力等价。

### 6.2 工作流运行器：执行加载的工程流程

负责解释受支持的流程定义、推进节点、保存运行位置、处理节点结果和阻塞。它不应内置唯一的软件工程顺序，也不从任意外置文字直接产生执行权限。

这里必需的不只是加载：还要知道当前运行采用哪个流程版本、节点输入是什么、结果保存在哪里、失败或中断后能否恢复，以及什么变化使先前检查失效。

可配置节点和可加载规则不等于允许执行任意代码。配置格式、扩展方式、隔离与可信来源需要后续专门设计。

### 6.3 工程材料管理：保存版本与关联

负责决定、依据、提案、DID、实施包和证据的版本与引用。不同文档可以有不同格式，但不能每个 Skill 各存一套独立且可修改的批准状态。

材料管理不负责决定业务方案。它保存“这项决定由谁、针对什么版本作出”，而不是替用户作决定。

### 6.4 审核与授权：意见和许可分开

审核可以由模型、工具或人工完成；授权来源是用户明确许可及有效项目规则。判断服务返回意见，运行机制检查这份意见及相应权限是否足以推进动作。

对于须经审核的正式变更，目标产品应使实际写入经过受控入口。如果其他入口仍能直接改写，就必须如实标为协作约定，不能宣称已形成强制关卡。

### 6.5 用户交互：同步认知，不只是显示日志

界面或会话负责向用户表达目标、关键变化、进度、偏差和待决定事项。来源应是可追溯的工作记录和证据，而不只是模型临时总结。

用户入口不必暴露所有内部细节；需要展开时能够查看依据与原始材料。解释当前正在做什么与索取批准是不同交互，不能用状态通知代替审批。

## 7. 外置工程方法包

“方法包”是本文建议的组织单位，不代表已决定新增一个具体 npm/Python 包或目录。

它可以包含流程定义、标准配置、Skill 和审核策略，各项有标识、版本及依赖关系。加载器识别支持的类型和版本；产品选择启用哪个组合。用户可以逐步改进方法，不必每改一次讨论顺序就修改运行器源码。

| 外置内容 | 规定什么 | 不拥有的权力 |
| --- | --- | --- |
| 工作流定义 | 阶段、依赖、输入输出、结果分支、回退位置 | 不自行授权副作用 |
| 文档标准配置 | 采用的标准版本、实质内容要求、适用与裁剪 | 不自行放宽用户承诺 |
| Skill | 完成某项操作的方法和输出约定 | 不维护第二份批准权威 |
| 判定策略 | 判断的问题、所需上下文、不确定时处置 | 不把分数变成许可 |

“不硬编码”的范围是具体工程方法，而不是所有机制都变成可任意重写的脚本。版本引用、权限检查、结果留档和证据真实性仍需稳定执行。

例如，原流程要求先生成接口文档再生成组件设计；后来发现某类小修复不涉及公开接口，可以通过经审的方法包裁剪这一步。不能通过流程更新偷偷取消原本有效的用户授权要求。

## 8. Decision 与 Jev 的独立性

用户提出将内置于 Pacthold 的 Decision 能力重新独立，以复用 Jev。方向是让判断成为可复用能力，而不是为每个新用途各写一个决策核心。

建议独立模块只接收事实、候选项和外部判定规则，进行必要的多轮调用，返回判断、理由、缺失信息与原始结果引用。它不内置“软件工程只有某些配置项”，也不内置 Profile 的完整业务结构。

```text
工程方法提供判定问题与上下文
              │
              ▼
独立判断能力 ──调用── Jev / 其他适用模型
              │
              ▼
意见与不确定性 → 工程运行机制处理下一步
```

Jev 可以用于某项 DID 增删改与依据之间的窄判定；是否适合、上下文需求和准确性需要实测。工程完整性审核、复杂解释和澄清不必全部交给 Jev，也不能预先认定一模型包办。

判定结果可以是支持、不足、冲突或无法确定；缺依据不等于用户反对。超时、输入不全或输出无法解释不能当作通过。

Decision 若还包含批准、状态写入或执行推进，不能整包不加区分地外移。独立的是判断能力；执行与状态权威继续由相应所有者维护。目标是减少耦合，不是造一个第二运行器或第二批准中心。

本文不核实当前 Decision 的实现目录和现存职责，也不批准其物理迁移。迁移前需要源码盘点，证明消费者切换、唯一权威与旧入口退役；不能只移动目录并保留旧运行链。

## 9. 自进化：改进方法，不改写事实与授权

用户希望流程与标准可以持续优化。建议把改进视为正常的、可审查的变更，而不是让 Agent 实时修改自己的通过条件。

改进来源可以是重复出现的歧义、遗漏、返工、错误阻塞、摘要失真和判定失误。系统可以收集证据并提出流程或标准修订，给出受影响案例和预期改善。

新版本在可复现案例上验证；既要检查能否发现真实缺口，也要检查是否把普通实现自由误报为必须由用户决定。通过率提高本身不证明标准更好。

变更经相应接受后形成新版本。运行中的任务固定方法版本；是否迁移到新版本是显式动作，并分析此前材料和检查的适用性。

以下属于设计底线建议，不能由普通方法更新自行取消：

- 意见、告知、接受和实施权限分开表达。
- 新材料不能自动继承旧版本批准。
- 未执行或失败的验证不能改记成功。
- 无法判定不能伪装通过，不能反复调整提示只为获取有利结论。
- 当前任务无法通过，不构成降低规则的授权。

谁可以批准方法更新、是否允许某些低风险变更自动接受、如何维护评测案例，仍需后续确定。本文没有授权无限自主进化。

## 10. 一次实际工作的示例

假设用户提出：“主控退出后不要关闭子 Agent，我明天要接着看。”以下是说明流程的示例，不是给产品新增这一行为。

记录可以确认退出时不随主控终止的意图，但不能顺便确定永久保留、十分钟超时、断电恢复和存储保留策略。

作者核对当前设计和实现，提出生命周期规则及受影响组件。确有重要选择未定时，给用户一个有上下文的问题，例如：退出后保留的是正在运行的进程，还是只要求重开后可恢复工作？两者的实现和验收不同。

依据审核发现“退出十分钟后自动终止”的条目没有支持，应返回作者或用户，而不是引用同一句话放行。工程审核进一步检查创建、退出、失败、恢复、权限及清理等适用要求有没有明确表达。

通过后，会话摘要解释具体改变、未改变的部分及风险。用户接受目标版本后更新 DID，再从差异形成任务：修改生命周期所有者、切换调用方、移除旧退出链、增加与批准行为相应的验证。

实施者不自行决定新的保留期限。核验分别展示成功场景、拒绝场景和未验证条件。若这次暴露了所有生命周期变更都易漏掉崩溃场景，可以另提标准改进，而不是偷偷改本次通过条件。

## 11. 当前材料、目标产品与未定内容

本轮已在个人 Skill 目录制作 decision-record、did-change-author、did-change-review、spec-package-review，并更新 did-change-to-spec；配有共享模板和版本/接受约定。这些是操作工具，不是 Ordessa 内已经接线的工作流引擎。

Jev 判定目前有输入输出接缝说明，不代表已有真实调用集成。Skill 格式检查不证明判定质量、标准合规或产品闭环。

尚未固定的实施选择包括：

- 工程方法包的文件格式、模式及可信加载边界。
- 流程运行器复用哪个成熟实现，以及怎样连接 agent-node。
- 工程材料的存储与唯一写入口、版本冲突和中断恢复方式。
- 具体 DID 编号、修订和项目裁剪。
- “未否认则暂准”的适用范围、触发条件和允许动作。
- Decision 独立后的公开接口与物理归属。
- 工程方法自进化的接受权限、评测与版本迁移规则。
- 首个产品闭环和实际交互入口。

这些不是要求用户现在逐条作决定，也不阻止先做事实盘点或原型；只是不能在生成实施包时无声填成确定要求。

## 12. 推进边界与完成判断

后续建议先验证一个范围明确的完整工程变更，而不是立即重构所有模块或引入完整大型工作流平台。验证对象应包括从讨论到可派材料，以及一次真实交接中意图与证据是否保持；具体范围和操作权限另行确认。

方向成功的标准不只是能运行流程或生成文档。需要证明：

1. 能找出会改变结果的未决选择，并变成用户能回答的问题。
2. 不要求用户决定已授权的普通实现细节。
3. 重要规定、版本、接受方式及任务之间有可检查关系。
4. 用户不阅读整包也能知道关键变化和待决定事项。
5. 替换工程方法不用重写核心推进逻辑；替换 Harness 不用重写整个工程流程，但能力差异不被隐藏。
6. 方法改进不会修改既有事实、吞掉失败证据或绕过授权。

本轮确定的是产品方向与工作关系；本轮没有冻结实现目录、接口、数据库或完整迁移计划。下一步的设计应以这份方向为依据，而不是将其中所有建议自动升级为批准需求。
