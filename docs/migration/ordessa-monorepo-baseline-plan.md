## 1. 目标和已经确定的方向

- 最终产品仓根目录就是 `/home/maoqh/projects/ordessa`，不在其中再嵌套一个新 Ordessa 产品仓。
- 产品采用 monorepo：一个产品提交标识自有代码及锁定依赖的组合，各组件保留明确包边界、测试和构建入口。
- 大仓与产品叫 Ordessa；后端治理核心及其 Python 包叫 Pacthold / `pacthold`；产品 Server 与核心分开。

- 旧实现保存在可恢复的历史与参考分支，不进入新 `main` 的有效源码树或默认构建。
- 允许基线携带明确登记的问题。UI 美化、所有 Harness 全面可用、Profile/Provider 成熟不是建立第一版基线的前提。

后续插件架构约定见 [插件组合与可验证解耦原则](ordessa-plugin-composition-principles.md)。基线建立后纳入主要架构文档；该文件区分必需依赖、可选集成和附属插件，不追加本轮全量重构要求。

## 3. 保存旧成果：历史、快照、运行数据分别处理

### 3.1 全量清点，但不读取秘密

按 Git common-dir 识别独立仓，避免把同仓几十棵 worktree 当成几十个仓。清点原仓引用、各工作树 HEAD/分支/真实路径、修改/删除/未跟踪项、符号链接，以及运行服务对路径的占用。

每个源码成果给出归属：进入新 main、进入参考分支、仍在独立开发、生成产物、用户运行数据、待确认。未知项不删除。对敏感文件只记录位置和处理策略，不读出或复制凭据内容。

### 3.2 保存提交与备份

- 已提交源码：保留原始提交对象及可达引用。
- 未提交源码：在保存分支或隔离副本形成 checkpoint，包含应保存的未跟踪源码和删除事实；不要在有其他写者的共享索引上直接整体 stage。
- 分阶段/未暂存差异若有独立意义，另存非敏感的状态清单与补丁；一个源码快照不能宣称恢复了原索引状态。
- Git bundle 包含原 refs 和新增 checkpoint；Git bundle 不保存未提交文件，必须先完成上述快照。
- 必须恢复到隔离目录校验：refs/提交可达、关键文件内容、删除状态、未跟踪源码是否完整。未保存成功前不进入目录移除。
- 原仓外的恢复备份拟放 `/home/maoqh/projects/ordessa-preservation/<批次>/`。这是建议路径，创建前检查存在性及写权限，不覆盖已有内容。不要放在待清理的产品根内作为唯一备份。
- 日志、数据目录、缓存、秘密不是“都进 Git 历史”的对象；保留原位并登记。需要迁移运行数据时另向用户确认。

### 3.3 新仓历史布局

保留两种引用：

1. `archive/<source-repo>/<source-branch-or-snapshot>`：保存各源线真实历史与 checkpoint，重名时使用稳定来源标识；保留来源→新 ref 映射。不能只复制最新源码后声称保留了全部历史。
2. `reference/hermes-desktop`、`reference/backend-legacy`、`reference/studio-legacy`：方便检出的精选参考快照，附来源、SHA、用途与许可证。不同有效源线不能未经审阅合成一个版本。

外部源仓对象可通过本地 fetch 等方式导入并建立可达分支，不要求把旧文件树合入 main。历史分支通常冻结；复用按能力提取到工作分支，不整体合并旧产品树。

归档 refs 会增加对象库体积，main 检出干净不等于 Git 历史很小。拟推送的历史需要核对敏感内容风险，检查工具只输出路径/命中类别，不展示秘密。发现风险停止发布，保留本地恢复能力后交用户裁定。

## 4. 新 main 的结构与职责

```text

    desktop/                      Electron 启动与产品组装
    server/                       Ordessa Server、接口、鉴权和 ACP 通道编排
  packages/
    pacthold/
      pyproject.toml
      src/pacthold/               治理核心及公共插件契约
    desktop-platform/             通用加载/宿主/原生桥与公共契约
  plugins/
    harness/
      src/                        Python 包建议使用 pacthold.harness_kit
      adapters/acp-adapter/        当前维护的 Go 桥源码和测试
      packaging/                  构建与依赖准备
      tests/
    commands/
    workbench/
    connections/
    agent/
      sessions/
      conversation/
    connectors/acp/
  products/desktop/               启用清单、依赖锁定、默认组装
  scripts/                       构建/启动/验证
  tests/                         跨组件集成验证
  docs/
    architecture.md
    baseline.md
    known-issues.md
    reference-index.md

  package.json                   npm workspaces
  package-lock.json
  README.md
  AGENTS.md                      新仓规则和当前权威入口
```

规则：

- 本图是职责与主要路径约定，不要求合并所有 platform/contracts 为一个巨型 SDK。其内部成熟的独立包可保留；迁移表必须明确归属。
- Server 应有自己的 Python 包（建议 `ordessa_server`）与依赖声明；Pacthold 使用 `pacthold`，避免两个发行包争抢同一普通 Python 包目录。
- 插件发行名称建议 `ordessa-harness`，其他自有包使用 Ordessa/Pacthold 命名；执行者应先一次性列清完整命名映射，再机械迁移。
- 新活动代码去除旧 `agent_box` / `agent-box` 包名、导入与启动入口。来源 URL、上游 Go module、许可证、历史文档可以保留旧名称并标明原因，不能盲目替换第三方标识。
- 现有数据格式、数据库版本、插件 ID、已有用户配置不随目录改名盲改。对可能破坏用户数据的名称逐项区分，给出最小迁移或明确的旧数据兼容范围。
- 产品消费 Harness 的公共启动/连接/关闭能力；桥路径、Pi CLI 等是 Harness 内部配置，可提供诊断覆盖入口，但不能继续要求产品默认脚本拼这些路径。
- 编译二进制不进 Git，依赖和工具链固定版本，脚本能够构建/准备运行工件。无需产品根 third_party 或 integrations 目录。
- 只移走确认不被当前基线依赖的模块；当前有效测试、迁移、资源文件、安装材料不能以“精简”为由删掉。
- Python 用各自 pyproject 与锁定方式，JS/TS 用 npm workspaces；monorepo 不要求跨语言用同一包管理器。
- 核心不反向依赖具体插件；插件不能穿透导入宿主私有源码。嵌套插件有明确公共契约、加载依赖和资源作用域，不因目录嵌套自动获得权限。

## 5. 独立发展的插件与旧 Desktop

- 清点并保护已有 Profile、Provider、Workboard 的源码和历史。不要漏掉第三区域，也不要因“今晚只推进两个”删掉 Workboard。
- Profile/Provider 可继续独立演进；本轮迁移不强制暂停其功能工作或把未验收成果接入 main。
- 根目录最终不能依赖 `repos/` 下的嵌套开发仓。与其当前写者协调后，将独立开发位置安排到产品根以外，或在具备证据后迁到对应 monorepo 工作分支；不得移动正在被写入的仓库。
- main 不为尚未接入的插件建虚假实现。接入时按 `plugins/profile`、`plugins/provider` 组织；同一插件的 frontend/backend 可以同目录、各自构建。
- 旧 Hermes Desktop 优先复用：依赖方向检查、公共 SDK/Context 注入、成熟 UI 组件及测试。避免把其全局状态、Hermes 专属连接和旧启动链整体带入新核心。

## 6. 当前目录如何成为真正的新根

先在产品根外的隔离候选目录完成 Git 历史导入、代码迁移和验证，最终正式根仍为 `/home/maoqh/projects/ordessa`。候选位置由 ZCode 核对后给出，不能在当前根上边归档边覆盖。

切换前必须明确：

1. 当前 `.git/.agents/.codex` 受保护目录的环境归属与允许的切换方式。权限不允许就报告给用户，不绕过保护。
2. 旧服务、会话和工具是否引用当前根内 worktree/运行目录；需要停止或移动时由用户确认窗口。
3. 旧 worktree 的 `.git` 指针及原仓管理记录如何保持有效。不能直接移动其父目录后宣称一切可恢复；采用适用的 Git worktree 管理方式或经过验证的恢复方案。
4. `control/` 的独立 Git 历史进入 archive/reference，仍有效的决策迁入新文档；新 AGENTS 明确新权威入口，旧队列不再是活动入口。
5. 原根内旧 archive/backups、repos/worktrees/releases、运行数据和独立插件分别去哪，逐项列出真实路径。符号链接的删除与删除目标必须区分。

最终 main 的源码树不包含旧工作区容器、嵌套 .git 仓、机器运行材料。宿主工具必须保留的受保护元数据可作为环境例外存在并忽略；如运行数据因现存服务暂不能迁出，明确标记目录切换未完成，不能用 .gitignore 冒充物理收口。

切换采用可恢复搬迁或保留旧目录，不以递归删除根目录完成。切换前交用户一张明确的 source→destination 表和恢复步骤；切换后重跑产品启动检查。只有用户确认不再需要旧工作树且恢复验证通过后，才移除对应工作树；不默认删除原仓对象库。

## 7. 远端：沿用 agent-box 仓库，保留历史演进

推荐沿用 `https://github.com/mmm-05610/agent-box.git` 的仓库身份。GitHub 仓库以后可以更名为 `ordessa`，本轮先准备方案，不调用远端改名或发布。

操作原则：

- 核实远端默认分支与最新提交，从其实际主线建立迁移候选；把旧 main 保存为具名历史引用。
- 让新的 monorepo 主线保留旧远端 main 的祖先关系。旧文件可以在迁移提交中移除，历史仍在；不要用无关 orphan main 强推覆盖。
- 把已经验证的候选版本接入这条祖先链时核对最终文件树，不能把远端未审阅的新代码隐含带入产品。
- Desktop、Studio、Control、桥等原仓历史以命名 archive/reference refs 保存；原远端暂时保留，后续是否设为只读归档由用户决定。
- 公布前重新确认远端没有新增提交；发生变化则重新整合和验证，不强推压掉别人工作。
- 发布应明确列出需推送的候选、历史引用、目标 main、备份引用。禁止 push --mirror、默认 force push、删除旧 refs。
- 用户当前确认的是远端沿用方向，不等于授权立即 push、替换远端 main、改名或删除远端。ZCode 将本地结果准备到可审阅，再由用户确认发布动作。

若历史安全或权限问题使原仓不适合复用，提供证据及新仓备选，由用户决定，不自行换方向。

## 8. 实施阶段及验收

### A：盘点和历史保全

产出仓库/工作树/dirty/source 清单、保存 refs 映射、独立恢复备份；恢复测试通过。未知成果、秘密、活动写者和受保护路径分别登记。不要停在盘点报告上，继续已授权且不依赖裁定的准备工作。

### B：候选 monorepo 与迁移

迁移表逐项关联原路径/原提交/目标路径/改名/保留或退役原因。构建候选仓，导入历史引用，完成命名、包边界、Go 桥归属和启动路径收口。动作分成可回退的小提交。

### C：验证并固化开发基线

| 门 | 通过标准 | 缺席/失败的处理 |
| --- | --- | --- |
| 历史恢复 | 原 refs 与保存成果可恢复、关键文件比对一致 | 不切换、不清理 |
| 干净检出 | 安装、构建、包资源与产品启动不依赖旧源码目录 | 报具体缺口，修复后只复跑相关项 |
| 改名完整性 | 自有活动导入/入口使用新名，历史及第三方例外有清单 | 不能只跑零命中正则冒充验证 |
| 依赖边界 | Pacthold 不反向依赖产品，插件通过公共契约接入 | 越界引用说明归属并收口 |
| 现有回归 | 对同一基线逐项区分新红与继承红，无未解释新增失败 | 不删断言、不用 skip 掩盖 |
| Pi 主链路 | 项目绑定、两轮、分片、工具审批/取消、历史与释放具有对应证据 | 未测明确标记，阻塞关键项交用户裁定 |
| 版本证据 | 源提交、锁文件、桥源码/工具链/工件、命令与测试一致 | 不引用过期报告替代新版本证据 |

受控测试与真实模型分开记。新真实模型调用先给用户次数/范围/费用上限并取得许可；可复用版本匹配的已有真实证据，不能要求为迁目录无限重跑。新增加的生命周期/边界行为需要能抓到错误的反例；纯路径机械迁移以构建、现有测试和安装验证为主，不强制为每行改名造测试。

已知延期项允许包括 UI 两问题、已分类旧链诊断、非本次范围的 Harness 能力；不得以“等完美”拖延开发基线，也不得把未运行产品写成已验收。

### D：本地根目录切换与 main

提供候选 SHA、差异、保存/恢复证据、source→destination 表和需要处理的活动服务。用户确认后执行切换，建立本地 main，验证根目录实际状态与关键启动方式。回报 BASELINE_ESTABLISHED_WITH_KNOWN_ISSUES 或具体未完成项；用户验收结论仍由用户决定。

### E：远端发布准备

输出精确发布 refs、main 祖先关系、可恢复引用、是否改仓库名及其影响，等待用户批准远端操作。当前会话无 push 授权。

## 9. ZCode 主代理与子智能体安排

主代理由用户以 GLM-5.3 运行，负责范围判断、共享契约、主索引/提交/集成和用户沟通。积极使用工具支持的子智能体，无需为每次只读分工另行问用户。

建议每批 3–4 个并行单元，受实际并发上限约束：

- 历史保全代理：仓库/工作树/未提交成果与恢复核验。
- 后端代理：Pacthold/Server/Harness 的路径与依赖迁移。
- 桌面代理：workspaces、平台/插件、构建和产品配置迁移。
- 审阅代理：独立检查漏文件、历史可达、旧路径依赖与声明失真。

Go 桥、旧 Desktop 复用索引、独立插件盘点可作为后续独立子任务。契约和共享根配置先由主代理确定；各实现代理在隔离工作树/副本或明确不重叠的路径工作。禁止多人操作同一 Git 索引；提交、合入与根目录切换由主代理掌握。不能把后端/前端合同各派一人分别发明。

旧源树按固定提交读取；存在活动写者时先约定快照，变化不能悄悄加入候选。主代理实际核对关键结果，不能把子代理的绿色报告直接当成主线通过。

允许在产品语义、历史保存完整性、权限、数据迁移、活动服务、远端发布上停下与用户确认。普通迁移细节、只读盘点、构建与隔离验证自行推进。发现问题及时报告，不连续尝试旁路或扩大整改范围。

## 10. 最终交付清单

- 正式根目录与本地 main 提交；公开接口和包命名表。
- 原仓/工作树 → archive/ref/checkpoint → 新路径的映射。
