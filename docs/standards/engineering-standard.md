# Ordessa 工程组织与模块边界规范

版本：v1 修订 4  
日期：2026-10-12  
状态：规范主体已确认，迁移补充约束纳入当前实施；实现是否达标须按实际检查验收  
适用范围：Ordessa 的 Python 与 TypeScript 单仓库、测试、插件、方法描述和工程文档

本规范让开发者与 agent 能自行决定代码归属、文件拆分、目录层级和依赖方式。目标是让修改有明确责任边界，并能被检查；文件更少、目录更深或名称更整齐，都不单独代表设计更好。

本文沿用已确定的整体架构，补齐工程执行规则。所有目录树均为目标结构或示例，不是对当前仓库的核验结果。已确定的结构边界优先于本文的一般组织建议；文件／目录的自主选择适用于尚未确定的内部细节，不授权改变已批准的目录安排。当前按已批准范围推进实施；本文件更新不表示代码已经迁移完成或通过验收。落地时先核对实际入口、调用方、打包配置和测试命令。

## 1 规则等级与决策权限

- **必须／不得**：合并门槛。偏离须有明确、限时的例外。
- **默认／应**：通常采用的方案。有具体反例时，开发者或 agent 可选择更合适的做法，在变更说明中解释即可。
- **可以／示例**：工具或实现选择，不构成必须创建的文件和目录。

**目标架构一经确认，即为实现与验收的前置约束。功能接通和测试通过不得以新增逆向依赖、重复权威或延续退役入口为代价。迁移按可验证的完整切片推进，结构收敛与行为回归同时验收；不得将结构清理降为功能完成后的可选优化。**

这里的结构优先，具体指责任 owner、依赖方向、公开 API 和唯一正式运行链，不能简化为目录看起来整齐。实现应从已确认的边界内形成可运行切片；遇到架构约束与目标的实质冲突时，报告具体入口、依赖、缺失能力与可选方案，交相应决策方处理，不静默牺牲结构换取测试通过。

普通的文件拆分、目录命名、局部帮助函数和测试布局，由实现者依照本规范决定，不逐项询问用户。新增顶层能力、变更既定职责归属、改变公开契约或验收语义、引入新的长期兼容义务，须作为架构决策评审。

四个概念分别判断，不混用：

1. **责任所有者 owner**：对某项能力、语义和公开契约负责的模块边界。
2. **文件／子目录**：该 owner 内部的组织手段，不自动成为新边界。
3. **语言包**：Python import package 或 TypeScript module/package。
4. **分发／构建单元**：有自身安装、依赖、构建或发布配置的单元。

新建目录不等于新建分发包；出现两个类不等于需要两个文件；出现两个调用者也不等于应建立全局公共层。

### 2.1 每个区域回答什么问题

| 区域 | 拥有的责任 | 不应拥有的责任 |
| --- | --- | --- |
| `apps` | 进程入口、配置读取、最终依赖装配、启动与关闭 | 工程规则、执行状态机、协议业务实现 |
| `interfaces/channels` | 用户或客户端交互、命令与请求适配、呈现 | 另写一套用例、审批或验收政策 |
| `interfaces/transport` | 客户端／服务端传输、连接与编解码边界 | 根据传输成功判定工程成功 |
| `interfaces/system-access` | 系统统一公开访问入口，路由至 EngineeringService、UnitManager、profile／environment 能力，聚合查询并提供安全投影 | 直接重写工程用例、执行机制或通用工具 |
| `interfaces/contracts` | 确有共用需求的接口／线上协议契约 | 收纳所有领域模型的中央仓库 |
| `engineering/domain` | 通用工程对象、局部不变量、评审／审批记录与事实绑定 | 具体方法的工作流和验收政策、进程管理、provider、UI 与网络操作 |
| `engineering/methods` | 方法描述语言的定义、加载、校验与编译 | 具体方法策略全集、执行引擎、领域对象总库 |
| `engineering/application` | 对外工程用例、应用契约与需求侧端口，按编译后的方法规则推进编排 | 自创方法政策、直接依赖 execution、UI 呈现或 provider SDK 细节 |
| `engineering/adapters` | 工程侧端口的具体适配与边界转换 | 新增隐形领域规则 |
| `execution/units` | agent 与 environment 的组合、执行单元生命周期及运行记录 | 工程成果是否被接受的最终判断、未经设计增加的 decision 依赖 |
| `execution/agents` | agent 配置、harness 交互与协议能力 | 完整 unit、环境生命周期、工程审批 |
| `execution/environments` | 环境能力与生命周期契约 | agent 思考或工程验收 |
| `execution/decision` | 独立的决策能力与调用边界 | 默认从属或依赖 units／agents／environments，替代方法规定的审批与验收 |
| `infrastructure` | 与工程语义无关的复用机制 | artifacts、reviews、unit 状态等业务事实 |
| `plugins` | provider 特有的 harness、environment、decision 实现 | 借 provider 名称重新组织核心领域 |
| 根目录 `methods` | 外部方法策略、工作流、评审与验收政策，以及方法所需资源 | 被核心随意扫描和导入的任意代码 |

`engineering/domain/packages` 指工程领域中的 package 概念，与仓库根的 `packages/` 组织容器不是同一含义。

旧 `kernel` 与 `c1-api` 不属于目标架构。不得为保留旧入口再建立一个新名称的万能核心，也不得把上述职责迁进新的中央转发包。

## 3 同级目录如何成立

同一父目录应有一个能解释主要子项的组织问题。例如 `interfaces` 回答“系统怎样被访问与呈现”，可同时包含渠道、传输、统一系统入口和共享契约；它们是协作角色，不必属于同一种实体类型。

必须区分三个关系：

- **归属关系**决定放在哪个父目录。
- **依赖关系**决定谁可以调用谁。
- **抽象程度**由接口和职责决定，不由路径深度决定。

因此，同级模块可以依赖，支持性模块可以与主要能力同级。`units` 可以使用 `agents` 与 `environments`，不意味着后两者必须搬到 `units/` 里面；`contracts` 可以支持兄弟模块，不意味着要给每个兄弟补一份 contracts。

新建同级项时，必须能说明：它负责什么、与现有兄弟的差别、主要调用者，以及允许的依赖方向。若只能说“这里暂时不好放”，应先回到现有 owner 内组织。禁止为了树形对称复制 `api/models/services/utils` 四件套。

## 4 从新增代码到文件和目录的决策

### 4.1 判断顺序

先确定语义 owner，再判断该 owner 内有没有合适文件；最后才考虑新文件、子目录或分发单元。不能先挑一个听起来通用的名字，再把代码塞进去。归属、拆分和抽象都不以消费者数量为硬门槛：即使只有一个消费者，独立生命周期或明确技术边界也可能足以成立。

| 场景 | 默认决策 | 升级为更大边界的条件 |
| --- | --- | --- |
| 一组小类型、函数共同表达同一概念，经常一起修改 | 放在一个有明确主题的文件 | 出现独立变化原因或不同依赖 |
| 一个 helper 只服务当前实现 | 留在当前文件，必要时使用私有名称 | 变得足够复杂，需要单独阅读或测试 |
| 同一 owner 的多个文件确实需要相同逻辑 | 在该 owner 内按职责提取 | 其他 owner 也需要且语义、稳定性一致 |
| 文件同时承担声明、I/O、策略判断、外部调用 | 按责任拆文件，先隔离副作用 | 拆出的多个文件构成稳定子能力 |
| 多个文件有共同职责、专属依赖或生命周期 | 建子目录并给出简短职责说明 | 它需要独立公开契约、依赖或发布边界 |
| 一个目录只是再包住同名文件 | 默认去掉这一层 | 框架要求、资源归属或明确封装边界 |
| 两个功能恰好有相似代码 | 先留在各自 owner，检查语义差别 | 能命名共同概念，抽取后不会产生反向依赖 |
| 需要独立安装、运行时依赖、构建或发布 | 建分发／构建单元 | 不以文件数量作为依据 |

### 4.2 何时拆文件

有以下证据之一时应考虑拆分：

1. 修改原因不同，例如调整模型字段与改变远程重试算法。
2. 依赖不同，例如纯计算与数据库／SDK I/O 混在一起。
3. 生命周期不同，例如导入时定义对象与运行时持有连接。
4. 阅读、测试或审查时必须反复跳过大量无关内容。
5. 多人持续修改互不相关的区域，且能识别稳定责任边界。

不实行“一类一文件”“一函数一文件”或硬性行数上限。一个概念所需的多个小类、异常和辅助函数可以同文件。拆分后应减少理解负担，不能形成必须打开六个文件才能读完十行逻辑的转发链。

可把手写源文件约 500 行设为人工复查提示，但不得直接据此拒绝合并或强制拆分。生成代码、schema、声明数据、表驱动测试及完整场景测试需分别判断；短文件同样可能违反职责边界。

### 4.3 何时建目录

默认先使用简单文件集合。新目录应把一个可命名的子能力及其紧密相关文件聚拢，或者实现确有需要的封装、资源或构建边界。目录没有固定最少文件数；一个文件也可能因发布或框架要求单独成目录，但不能以“以后可能会扩展”为唯一理由。

删除最后一个实现时一并删除无意义的空目录和占位文件。不得为了展示愿景创建空的 `api/`、`ports/`、`models/`、`services/`、`adapters/` 树。

### 4.4 文件升级为目录的具体判断

以下仅为拆分判断示例，不是新增模型或目录的迁移指令。例如，artifacts owner 起初只需要 `ArtifactRef`、`ContentKind` 及几个共同变化的小类型，一个 `models.py` 足够。后续内容描述与来源证明各自形成多种模型、独立规则和独立测试时，可以升级：

```text
# 初期：一个紧密概念群
artifacts/
├── models.py
└── validation.py

# 演进后：两个真实存在、可独立维护的模型群
artifacts/
├── models/
│   ├── __init__.py       # 仅保留实际需要的公开导出
│   ├── content.py
│   └── provenance.py
└── validation.py
```

这里的新目录仍属于 artifacts，不是新 owner 或新分发包。若两组内容都很小且总是一起变，仍可留在 `models.py`；若只有 I/O 校验逻辑变复杂，应提取校验实现，不能把 `models.py` 机械切成编号文件。TS 同理，可由 `models.ts` 演进为 `models/content.ts` 等；是否需要 `index.ts` 由公开入口决定。

如果新增的是与 artifacts 并列的工程能力，例如 reviews，它应在 domain 下成为兄弟 owner，而不是塞进 `artifacts/models/`。判断依据是“谁对这项语义负责”，不是哪一边当前文件更少。移动时同步导入、测试和必要公开入口，验证实际安装／构建后的路径。

### 4.5 示例

合理：责任明确，文件承载完整概念，只有形成子能力时才加层级。第一个例子仅说明尚未冻结结构的小模块如何组织，不用于折叠上文已批准的 `engineering/methods` 目录。

```text
<尚未确定内部结构的小型描述解析模块>/
├── definitions.py      # Method、Step 及紧密关联的声明
├── loading.py          # 显式来源读取与解析
├── validation.py       # 引用关系和方法语义校验
└── compilation.py      # 编译成下游消费的计划

agents/harness/protocols/acp/
├── client.py           # 协议交互
├── session.py          # 会话生命周期
└── payloads.py         # 必要的协议类型或透明封装
```

不合理：按语法元素机械拆分，并用目录和转发函数凑层次。

```text
<同一小型描述解析模块>/
├── classes/method/definition.py
├── classes/step/definition.py
├── functions/load_method/load_method.py
├── services/manager/service.py
└── utils/common/helpers.py
```

另一个不合理例子是把 `Review`、`UnitResult`、ACP 消息和 HTTP DTO 全放入全局 `models/`，再要求所有区域通过 `kernel` 访问它们。这会掩盖所有权，而非建立复用。

## 5 命名与语言布局

- 名称优先表达业务概念或真实行为，例如 `review_record.py`、`session.py`、`compile_method.py`。避免没有限定范围的 `manager`、`processor`、`misc`、`utils`；既定公开能力名如 `UnitManager` 不在此列。
- Python 文件和 import package 使用 `snake_case`；TS 文件默认使用 `kebab-case`，类型／类采用语言惯例。已有构建单元的稳定风格优先于零散改名。
- 同一概念保持一个名字。不得用 `core`、`base`、`common`、`shared` 为相同职责创建多个近义入口。
- Python 可安装单元默认采用 `src/<import_name>/`，测试放该单元的 `tests/`。这是本项目默认选择，用于避免测试误用工作目录中的源码；不要求把每个逻辑目录单独打包。参见 [PyPA 的 src 布局说明](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)。
- TS 构建单元默认有 `src/`；内部单元测试可邻近源码。一个单元统一采用一种主要布局，不为追求 Python／TS 对称而强制相同目录。
- `pyproject.toml`、`package.json`、`tsconfig` 等只在真正需要的工作区或构建边界出现。不得为每个职责目录创建配置和独立版本号。

物理布局示例，不是新增分发单元清单：

```text
<某 Python 构建单元>/
├── pyproject.toml
├── src/<import_name>/...
└── tests/...

<某 TS 构建单元>/
├── package.json
├── tsconfig.json
└── src/
    ├── review-panel.ts
    └── review-panel.test.ts
```

## 6 公开 API 端口与依赖

### 6.1 边界规则

**必须：**跨 owner 依赖其声明的公开 API 或契约；不得导入对方私有实现。公开入口可以是 `api.py`、明确的公开模块、精简的 `__init__.py`，或 TS 的导出入口／受支持子路径，不强制所有模块都建一层 facade。

同一 owner 内可以直接导入内部文件，不必先绕回自己的 `__init__.py` 或 `index.ts`。统一使用 barrel 并不能自动建立边界，反而可能制造循环和无意义重导出。

owner／包的架构边界依赖图必须无环，也不得存在导致运行时初始化问题的循环。`TYPE_CHECKING`、`import type`、延迟导入和字符串反射不授予跨边界例外；类型依赖也须满足架构方向，不能仅让运行时不报错便宣称已解环。同一内聚模块内部的类型引用不自动构成架构环，例如为局部错误注解引用关联类型，需根据实际边界与初始化行为判断。确需共享的契约移到真实的语义 owner 或需求侧端口，不移进万能 common。

Python 的私有模块限制需要静态检查和审查配合；`__all__` 不是访问控制。TS 使用与实际运行环境匹配的解析模式和包导出，禁止通过 `paths` 直接指向兄弟包源码来绕过公开边界。`exports` 的解析条件及 `paths` 的影响参见 [TypeScript 官方模块参考](https://www.typescriptlang.org/docs/handbook/modules/reference.html#packagejson-exports)。

### 6.2 依赖方向

- `engineering/domain` 与 `engineering/methods` 是互不依赖的底层模块，也不依赖 application、interfaces、execution、具体 adapter 或 plugin。前者定义工程事实与不变量，后者解释方法描述。
- `engineering/application` 使用 domain、methods 及自身需求侧端口；端口可放在既定的 application contracts 内，不为名称齐全再造一层。application 不直接依赖 execution；工程 adapter 对接 execution 的公开 API。
- 渠道经 system-access 的统一入口访问系统能力，不直接拼装领域流程；入口将请求路由到相应公开服务。
- `execution` 不依赖工程用例或 interface 渠道。unit 组合 agent 与 environment；decision 与 units、agents、environments 保持独立，不因同在 execution 下就建立默认依赖。
- `infrastructure` 不反向依赖上述业务区域；具体 provider 依赖它实现的端口或公开契约，核心不反向导入具体 provider。
- `apps` 作为最终装配根，可以知道具体插件与适配器，但必须通过它们的受支持入口装配。它不因此获得复制核心逻辑的理由。

这些是允许关系的边界，不是每个模块都必须建立的依赖。新增依赖仍需说明实际用途。

端口描述调用者真正需要的能力，放在需求所属的边界；实现放在 adapter 或 plugin。默认采用明确参数、函数、结构化接口或 `Protocol`，不要求每个接口配抽象基类和继承体系。只有存在可替换边界或独立测试等实际需要时才抽象，不为一次内部调用建立端口。可直接复用的通用库或 infrastructure 能力不必再包 adapter；也不得仅靠导入类型制造表面上“齐全”的层次。

### 6.3 装配与导入副作用

`application/assembly` 组合工程用例及已传入的依赖，`units/assembly` 组合 agent 与 environment，`apps` 选择具体 adapter／plugin 并完成最终进程级接线。它们不得各自再实现方法政策。用例可以承载完整、有意义的业务动作，不要求拆成大量原子转发函数。

模块导入不得启动进程、打开网络连接、扫描工作区、初始化数据库或触发任务。资源获取、关闭、超时、取消和所有权须在明确的运行生命周期中处理。注册插件不得依靠不可控的全目录导入副作用。

## 7 模型定义与处理行为

### 7.1 一个语义 一个所有者

公开模型必须有单一权威定义：工程事实归 domain，应用请求／结果归 application contracts，执行定义和记录归 execution，线上表示归对应接口契约。

传输 DTO、UI 视图或持久化表示可以与领域模型不同，但须有明确目的，例如版本兼容、隐私裁剪、序列化或展示，并由边界转换负责。不得只为“每层都要有模型”复制同义字段，再长期手工同步。

跨语言契约须选择一个权威源，例如 schema 或一侧模型；生成另一侧表示并校验同步。生成物是源的投影，不是第二个可以独立编辑的事实来源。并非所有内部对象都需要 schema 或跨语言生成。

### 7.2 definitions 放什么

`definitions` 默认只含声明、枚举、类型、默认值，以及保证对象自身成立的局部不变量。允许无 I/O 的归一化与本对象验证；不得在构造对象时读取文件、解析任意输入、访问网络、装配依赖或推进执行流程。

职责区分如下：

- `loading`：按明确来源读取、反序列化和解析外部描述；复杂解析逻辑可在该区域内再拆分。
- `validation`：检查跨对象引用、完整性及方法约束；需要外部事实时显式传入或通过声明的端口获取。
- `compilation`：把已理解的描述转换为可消费计划，并保留可定位到源描述的错误信息。
- `assembly`：选择和连接实现、配置及依赖。
- `lifecycle`：管理运行期间的状态转换、资源和结束原因。

这些是责任分离，不是调用必须穿过的固定五层。若一步很简单，可直接调用已有函数；不得为凑目录增加单函数转发壳。

### 7.3 common 的准入

`engineering/domain/common` 只放多个工程子域确实共同使用、含义稳定的值类型或基础约束。它不得枚举所有 owner，不得导入具体子域，不承担注册中心、流程协调或全域异常大全。只属于 artifacts 的 ID、状态或错误，仍由 artifacts 拥有；被其他区域引用不改变归属。

## 8 Ordessa 特有的实现边界

### 8.1 unit 完成与工程验收

unit 负责说明“执行发生了什么”：开始、结束、取消、失败、运行结果及结束原因。`completed` 或进程退出码为零，不能自行推导“工程成果已通过验收”。外部 methods 定义工作流、评审与验收标准；application 执行编译后的方法规则；domain 维护通用工程对象、不变量及结论与记录的绑定。不得在 domain 中硬编码某种方法的通过标准。

不得在 harness、environment、日志工具或 UI 中暗藏另一份验收规则。缺少方法要求的报告时，应明确呈现缺失及其工程影响，不把执行成功包装成验收通过。

### 8.2 方法与外部策略

`engineering/methods` 是解释机制。根目录 `methods/` 承载外部方法与具体政策，不把每个策略硬编码成核心分支。方法解释器与 domain 保持互不依赖，由 application 将方法计划用于工程动作。

方法要求哪些报告和验证项，应在方法契约中明确声明。engineering 只接收经公开端口明确提交的 required reports，不自行遍历工作区、读取外部业务代码或建立通用文件收集器。方法委派的 worker／checker 可以在授权范围内读取目标代码并提交检查报告，解释器读取方法声明也不等于直接检查被治理代码。

路径或 payload 引用仅在具体方法确有要求时作为报告字段存在，不据此增设全局产物扫描或注册系统。不得因发现同名文件就视为满足要求，也不得通过扫描外部方法或 agent 源码猜测“应该产出什么”。报告是否满足方法要求由应用机制按编译结果判断。

### 8.3 ACP 与 provider

ACP 协议层负责实际协议交互与版本适配。原生 payload、标识、扩展信息和错误语义在允许保留的范围内透明保存或传递，不先压成一套 Ordessa 自创的“通用 agent 协议”再翻译回来。

产品确需统一展示或调用时，可以提供小而明确的投影；投影说明映射与信息损失，不能取代原始协议事实。原生 payload 可能含敏感内容，保留范围仍受权限、脱敏和保存期限约束。

provider 特有 SDK、启动参数及兼容处理放在 `plugins` 对应实现中；协议公共机制放在 `agents/harness/protocols`。不因多个 provider 都有 session 就提前抽取一个限制所有协议表达能力的基类。

### 8.4 何时新增 infrastructure 能力

在既定 `infrastructure` 区域内新增一个能力，必须同时满足以下条件：

- [ ] **有当前需求和明确调用方。** 能指出哪个已存在或本次正在实现的调用方需要它，以及要解决的实际技术问题；“以后也许有用”不足以成立。
- [ ] **不包含业务判断。** 它表达技术机制，不需要知道 Unit、review、工程方法或用户批准的业务语义，也不反向导入业务模型。调用方可传入普通上下文字段，但机制不解释其业务含义。
- [ ] **统一有实际价值。** 它处理资源释放、原子写入、日志上下文／脱敏等明确问题，或建立必要的一致行为；不能只给标准库函数改名，再加一层无意义转发。
- [ ] **已检查现有能力。** 先查语言标准库、已采用的依赖和仓库内实现。可直接复用就复用；在现有模块扩展即可解决时，不另造近义能力。
- [ ] **有清楚的边界和验证方法。** 能说明输入输出、必要依赖、资源或错误行为，并可独立测试。接口按需要保持简单，不要求每个函数都配端口、基类或 adapter。
- [ ] **放在这里比留在 owner 内更合理。** 说明统一的技术约束或独立生命周期为什么值得集中维护；纯粹服务某项业务实现的局部 helper 默认留在原 owner。

**不设“至少两个消费者”的硬门槛。** 一个调用方也可能确实需要独立的技术能力，例如可靠的连接池生命周期；反过来，两个调用方有相似代码，也不能证明它们共享同一语义。是否新增取决于上述理由，不取决于预测中的复用次数。

| 可以进入 infrastructure 的例子 | 应留在业务 owner 的反例 |
| --- | --- |
| 统一日志配置、上下文传递和通用脱敏机制 | 根据日志或报告判断 review 是否通过 |
| 临时文件写入、同步和替换组成的原子写机制 | 判断哪份工程报告应被接收或验收 |
| 通用数据库连接／连接池的创建、超时和关闭 | 工程对象存储映射、验收状态推进或方法特定查询 |
| 通用资源清理与失败后的释放机制 | 判断 unit 完成是否代表工程接受，或把用户回复判为批准 |

这些例子说明准入边界，不是要求现在实现的能力清单。`infrastructure` 默认保持扁平；单一、内聚的实现可用一个文件，形成多文件子能力后再按第 4 节建目录。新增能力不默认产生新的 Python 分发包或 TS 工作区包。

满足规则且处于已批准的 infrastructure 范围内时，由执行者自行选择文件或目录，交 Sol 牵头审查，不必请用户逐个批准。新增顶层架构层、改变既定依赖方向、扩大权限或引入尚未获准的外部访问，属于另一类决策，必须先走相应评审或授权；不能借新增基础设施能力顺带完成。

### 8.5 统一日志机制

日志作为统一的通用机制，约定必要的级别、事件信息和上下文字段，按需支持关联标识、结构化输出与脱敏；输出目标及配置在装配根决定。Python 默认优先复用标准库 logging 的真实接口与既有能力，例如 `getLogger(__name__)`、handler 或上下文适配器；跨运行时统一通过必要的最小契约或薄适配实现，不要求所有业务代码继承 Logger，也不强造庞大的日志框架。[Python logging 文档](https://docs.python.org/3/library/logging.html) 提供其模块级 logger 与集中配置方式。

诊断日志可以用于排障，但不得代替权威的 unit 运行记录、工程评审或审批证据。必须可从正式记录说明状态及决定，不能依靠解析某句日志恢复唯一事实。

## 9 测试 配置 资源与生成文件

### 9.1 测试归属

- owner 的单元测试随其构建单元组织；Python 默认 `<单元>/tests/`，TS 默认邻近源码。测试名称描述被验证行为。
- 跨独立构建单元的集成测试与系统端到端测试放顶层 `tests/`，按场景组织，避免复制整个生产树。构建单元内部的集成测试保留在该单元 `tests/`，消费者拥有的契约测试也可随消费者放置；不因涉及两个内部子模块就一律上移。
- 测试公开边界时通过公开 API；测试 owner 内部算法可以直接访问内部模块。不得用跨 owner 的白盒测试为生产代码越界提供借口。
- fixture 放在最小共享范围。Python `conftest.py` 只覆盖需要它的测试树；全局 fixture 不隐式联网、读取私人凭证或修改工作区。
- 测试数据与样例明确区分，固定随机种子或控制时间等不稳定源。默认测试不得依赖真实付费服务；外部集成测试须显式启用并说明前提。
- 关键覆盖包括失败、取消、重试、重复事件、资源关闭、缺报告，以及“unit 完成但工程未接受”。不以测试数量或单一覆盖率取代行为证明。

pytest 支持不同测试布局和 import 方式；本项目的默认布局是本地选择，而不是声称框架只允许一种。参见 [pytest 官方集成实践](https://docs.pytest.org/en/stable/explanation/goodpractices.html)。

### 9.2 配置和资源

配置项的解释与校验归使用它的 owner；入口负责读取并传入。核心不得在任意文件中散读环境变量或猜测工作目录。共享配置仅放真正跨单元的工具规则，局部覆盖应说明差异。

运行需要的模板、schema、静态资源随其 owner，按构建系统声明打包；不得依赖“仓库里正好有这个文件”。开发样例不得被生产代码当默认数据加载。

凭证、令牌、私有运行输出和真实个人数据不得进入源码、fixture、测试 golden／snapshot、日志示例或生成物。这里约束的是测试与版本化材料，不禁止运行时 UnitSnapshot 保存其契约允许的标识和状态；实际运行数据仍按权限与保存政策处理。`.env.example` 仅列键名及无害占位值；敏感值由环境或批准的凭证机制提供。

### 9.3 生成文件

生成文件须可识别来源、生成命令及必要工具版本；明确禁止手改。生成物是否入库由消费方式决定：需供使用者直接消费的可入库，纯构建缓存不入库。不得因“自动生成”绕过机密扫描和许可证检查。

在适用的 CI 中重新生成并检查差异，或验证产物与源的一致性。不要同时维护手写 schema、手写 Python 模型和手写 TS 模型三份权威定义。

## 10 文档与仓库根目录

建议以 `docs/standards/engineering-standard.md` 为唯一正文；仓库根 `AGENTS.md` 保留精简执行要求和链接。不要复制成多份几乎相同的“开发规范”“agent 规范”和“架构清单”。

`README.md` 说明项目用途、最短可用路径和文档入口；稳定架构决策放 `docs/decisions/`。`docs/archive/` 可保存注明历史状态的旧方案，但不是当前实施依据；`docs/implementation/` 可保存受控、可版本化的实现说明和验证证据。模块 README 只在其边界、使用方法或特殊约束不能从代码和父文档看清时添加，不要求每个目录都写一份。

仓库根仅保留整体说明、许可证、安全或贡献说明、必要工具配置与工作区清单。任务笔记、运行报告、临时脚本和生成输出不随意堆在根目录。确需留存的验证报告放受控文档位置，提炼检查命令、结果与证据，排除原始秘密日志。

`scripts/` 默认承载薄命令入口；若仓库已有 `tools/`，可承载需要复用、独立测试的开发工具实现，不为统一名称强行重命名已有结构。维护脚本若已有正式能力，应调用其公开接口，不复制产品逻辑。

依赖规则以可执行检查配置表达可机器判定的部分；正文解释语义与例外。不得另建一个手填目录 manifest 与真实树长期双轨维护。标准或公开边界改变时，在同一变更中更新相关文档与检查。

## 11 自动检查与人工审查

落地检查从现有工具链出发，先保证能稳定运行，再逐步加强。不得承诺静态扫描可以证明完整架构正确，也不得用“规则文件已存在”代替实际执行。

| 检查 | 适合自动化的内容 | 仍需人工判断 |
| --- | --- | --- |
| import 与导出 | 禁止边、私有导入、已识别依赖环、类型导入、TS 公开入口 | 动态导入的真实语义、接口是否过宽 |
| 安装与构建 | Python 安装产物导入、TS 构建与类型检查、资源打包 | 分发边界是否必要 |
| 生成契约 | 重生成差异、schema 兼容性或契约测试 | 投影是否有意义、语义是否重复 |
| 行为测试 | 确认用例、运行生命周期、错误与取消路径 | 政策归属、验收证据是否充分 |
| 工程卫生 | 格式、静态类型、机密扫描、生成文件标识 | 命名质量、拆分是否改善理解 |

检查应纳入仓库内 Python 与 TS 的受控源码，明确生成物、测试和第三方 vendor 代码的处理方式。不能只扫描运行时 import 而漏掉类型依赖，也不能把仓库外方法包和第三方源码的内部结构纳入核心目录规范。

架构检查默认阻止新增违规。迁移期间的既有债务逐项列入窄范围、可定位的例外，不能用全目录忽略或长期基线掩盖新增问题。每个例外包含具体路径／规则、原因、负责人、退出条件及到期日；到期必须消除或重新评审。

提交结果需写明实际运行的命令与结果。未运行、环境阻塞、跳过和通过必须区分；文件数、测试数、覆盖率或扫描命中数都不能单独证明改造完成。

## 12 迁移与多 agent 协作

### 12.1 同一职责只保留一条正式运行链

**必须：同一职责、同一操作只有一条正式且权威的运行链。** 新路径完成接入后，不能继续由旧路径承担同一职责，形成两套入口、模型、状态机、持久化写入或装配方式。把新代码放进目标目录，不等于正式系统已经使用它；旧入口改成转发层，也不等于旧入口已退役。

迁移中尚未接入的实现可以短期存在，但必须记录负责人、共存范围、当前权威路径、退出条件和截止日期。若确需灰度切换，必须明确路由条件和各自覆盖范围；每个操作仍只能进入一条权威链，不能在新链失败后隐式回退旧链，或让两套状态机、双写逻辑同时处理同一操作。运行时路由及例外须可检查，不得藏在配置默认值、异常处理或测试辅助代码中。

本规则不禁止必要的多 provider 实现、隔离的测试替身、历史数据读取兼容，或在既定边界内开发新能力。它限制的是同一责任的重复权威实现，不是永久冻结候选目录、要求所有新能力等待全仓迁移结束，或用“一条链”取消有明确用途的可替换实现。

### 12.2 先盘点 再按完整调用链切换

迁移前必须从代码和实际构建配置盘点下列项目，不能只参考旧文档或搜索一个目录名：

1. 公开入口与全部已知调用方，包括 CLI、服务端、workbench、插件入口和脚本。
2. 公开模型、内部状态模型、状态转换，以及持久化的读写方和数据格式。
3. 正式装配根、注册表、依赖声明、导出表及相关配置。
4. 单元、契约、集成、端到端测试，以及 demo 所使用的实际调用路径。

为本批迁移标明旧责任的新 owner、公开入口和唯一权威路径。以完整、可验证的调用链为批次，在同一可合并变更中同步切换受影响的调用方、装配、测试、配置和文档。若一次不能切完，先划定互不重叠的迁移范围并满足 12.1 的限时共存要求，不能把“以后清理”作为开放式退出条件。

每个完整切片按以下顺序推进：

1. 确定目标 owner、公开入口及旧路径的退出条件。
2. 在目标位置补齐该切片必要的实现，不先给旧链继续扩展功能。
3. 切换本批调用方与正式装配，迁移行为断言并运行相关测试。
4. 在满足安全门槛后，同批删除旧路径并重新验证结构与行为。
5. 本切片达到迁移关闭条件后，再推进下一切片。

上述顺序约束同一迁移链；互不依赖且写入范围不重叠的切片可以并行，各自独立验收。不能借推进下一片掩盖上一片未退役。这不要求一次性搬空全仓、预建整棵空目录树或接受长期不可运行的大改。切片应足够完整以证明正式调用链成立，也应足够小以保持可验证、可审查。

切换后的 demo 和端到端测试必须经过正式公开入口与正式装配。不得为了让测试变绿，另写一个生产不会使用的成功路径、特殊 service 或绕过正式状态机的组装方式。单元测试仍可使用明确的替身，但替身不能冒充真实接入证据。

迁移必须保留应继续成立的行为保证，将对应测试迁到正式路径。测试失败时先判断真实行为或断言是否应改变；旧测试绑定退役入口时，应迁移行为断言，不能仅为变绿而恢复旧运行链。不得通过删除回归测试、跳过失败场景或只保留新路径的简单成功案例来宣布完成。大范围移动文件时避免混入无关重写。

### 12.3 清理优先级与安全顺序

**迁移清理采用事件触发的硬优先级，不能只登记一个到期日。** 出现以下情况时，执行者必须立即提出并推进对应动作，由牵头者调整当前任务顺序；不得持续以新增功能挤占清理，也不必等待整个项目改造完成。

| 触发条件 | 必须采取的动作与优先级 |
| --- | --- |
| 替代能力已就绪，调用方已切换，相关回归已通过 | 在本批变更中删除旧实现并重新验证，不能等“全部功能做完” |
| 两套状态、接受判断或装配使权威归属不清 | 先确定并收敛权威运行链，再向该职责增加功能；不能让新增逻辑同时适配两套事实 |
| 旧路径造成反向依赖、构建／测试阻塞，或新改动必须重复维护两套逻辑 | 将清理或完成必要替代能力列为当前任务的前置工作，先消除阻塞再继续无关功能 |
| 新调用方准备使用已明确退役的入口、模型或路径 | 立即拒绝新增旧依赖，接入目标公开 API；目标能力不足时明确补齐缺口，不扩散旧链 |
| 盘点确认旧实现已无有效运行调用方，也无获准兼容需求 | 本批删除旧实现及无用导出、注册、配置、依赖和空目录，不为未知的未来用途保留 |

因替代能力尚未具备而暂缓清理的，每项必须写出**确切缺失的能力、负责人和下一检查节点**，同时保留共存范围、权威路径、退出条件及截止日期。下一检查节点应是具体能力交付、调用方切换或验证结果，不得只写“后续优化”“有空再删”或“全部功能完成之后”。触发上表条件后，清理自动提升优先级，原截止日期不能成为继续等待的理由。

安全顺序是：核实调用与兼容需求，补齐必要替代能力，切换本批调用方与正式装配，通过相关回归，删除旧链，再验证无遗留引用与行为退化。替代、切换或回归门槛尚未满足时，不盲删仍在使用的实现；应优先完成门槛，而不是无限期推迟。已确认没有有效调用方的死代码，无须虚构一个替代实现才可删除。删除运行代码也不等于获准永久删除历史数据。

**迁移不能在“新实现写完”时关闭。** 必须同时满足：新链承担权威职责、受影响调用方已切换、旧链已删除或仅留获准的最窄兼容、回归通过且证据齐全。真实外部兼容或历史数据读取只豁免确需保留的窄适配，不能作为保留整条旧运行链的理由。

#### 用户明确指定优先级时的执行约束

用户明确要求优先清理某条旧链，例如 `kernel`，该目标必须成为当前主工作计划，列明剩余调用方、各项责任的目标 owner、必要替代能力和可删除批次。不能因为依赖多、改动复杂，就在未报告的情况下把它降为后续事项。

- **只有真实前置工作可以先做。** 能证明直接解除本批迁移阻塞的能力补齐、调用切换或相关回归，属于该优先任务的进展；无关测试、新功能或一般整理不能替代它，也不能被用来报告该任务“持续推进”。
- **阻塞必须具体。** 报告精确文件／入口、依赖或剩余调用方、缺失的替代能力、建议动作，以及由谁决定。不得只说“依赖较重”“还在处理”或等待用户主动追问。
- **既有权限内自行决策。** Sol 牵头处理既定架构内的拆分、顺序和实现选择；只有改变架构、公开行为、授权范围等事项才升级到相应决策方。发现困难不自动等于必须等用户指示。
- **检查节点必须有可验证推进。** 每个约定节点要么减少旧调用方／旧运行代码，要么关闭一个已识别的前置条件，并给出具体证据。二者均未发生时，主动报告停滞原因并重排下一步，不能以其他任务的完成量掩盖。删除数量只是核查线索，不能通过改名、合并文件或删测试虚增进度。
- **不得静默降低优先级。** 需要调整优先级时，先由协调方明确决策并向用户说明原因、影响和恢复条件；涉及用户目标、外部行为或权限变化时，取得相应确认。内部排期不能悄悄替换用户已经指定的目标。
- **协调方承担核查责任。** 牵头协调方应主动对照主计划检查剩余旧调用方、已解除阻塞和下一删除批次，不能只转述执行者在其他事项上的进展。未达到迁移关闭条件时，仍按未完成管理。

### 12.4 旧实现退役与有限兼容

完成一批迁移时，必须删除已失去用途的旧运行实现、公开导出、入口注册、依赖声明、配置分支和空目录，并更新相关锁定文件。仅停止直接调用、改名、保留别名或添加 forwarding wrapper，都不构成退役。不得用新的 legacy 门面继续承接 `kernel`、`c1-api` 或同类旧核心职责。

兼容须有可核实的需求，例如真实外部消费者尚未切换，或历史持久化数据确实需要读取。经明确评审后，只建立所需的最窄适配，并记录服务对象／数据范围、负责人、期限或复审时间、撤除条件和测试。不能用假设中的消费者保留整套旧引擎。

历史数据的只读解码或格式转换，可以独立于新运行链存在；读取结果应进入当前权威模型与机制，不重新启动旧工作流、旧状态机或旧写入链。测试 fixture 可以有意保存旧格式或不同实现的样本，须标明用途，不得被正式装配误加载。

历史方案和迁移前说明可移入 `docs/archive/`，明确标注已失效，不作为当前执行依据。归档文档不授予保留可运行旧代码、兼容入口或隐藏依赖的理由。

### 12.6 协作方式

采用 Sol 牵头、多个 Luna 执行的安排时，由牵头者维护本轮目标、公开契约和集成顺序；执行者承担明确、互不重叠的写入范围。模型名称不改变同一套工程要求。

- 分工以 owner 或完整小能力为单位，不按“一个人改类型、一个人改全部调用者”制造交叉写入。
- 开工前约定允许修改的路径、输入／输出契约、验收命令和不得触碰的范围。
- 共享契约变更由牵头者协调，指定一名写入者；先更新契约，再让依赖方基于确认后的版本推进。
- 跨范围修改、接口分歧、未授权变更或阻塞立即回报。不得覆盖、回滚或删除其他执行者的工作来让本分支通过。
- 局部检查完成后，由牵头者运行集成检查并审查边界；汇总报告不能把执行者的“做完”直接等同于工程验收通过。

遵循已批准规则即可自行执行的局部组织决策，不回交用户逐个批准。只有改变已定架构、外部契约、重要政策或授权范围时才升级决策。
