# Ordessa 进展与交付规范

版本：v1  
日期：2026-10-13  
适用范围：Ordessa 的整体改造、模块切片、编码、联调、验收与交付

本规范规定如何计划、报告和交接工作，不替代产品需求、架构决策、测试规范或用户授权。实现和迁移仍遵循 [工程组织与模块边界规范](engineering-standard.md)，特别是其依赖边界、行为验证与迁移收敛要求。文档中的状态和数量用于定位工作，不单独构成完成证据。

## 1. 一份总计划，阶段和健康分开

当前项目或专项的唯一总 TODO 固定在 [TONIGHT-DELIVERY.md](../implementation/packages-convergence-20261012/TONIGHT-DELIVERY.md)。本轮现有编号 **（6）至（14）是稳定 ID**，不得重编号、复用或因任务改名而改变。其他计划、handoff、进展摘要可以引用 TODO 的稳定 ID 和证据路径，但不得复制另一份可独立修改的总清单。局部模块可保留实现细节清单；它必须由总 TODO 引用，不能形成第二套总体状态。

计划先呈现整体目标、交付边界、模块 owner、依赖顺序和阶段退出条件，再把目标拆为各 owner 可独立执行的模块切片。每个切片说明输入、输出、公开接缝、允许修改路径、依赖方、验证场景和交接对象。并行切片必须写清写入范围不重叠；同一纵向调用链上的前置能力、正式装配、调用者、测试和数据责任不得拆成互相等待的孤立任务。

阶段描述工作所处位置；健康描述工作是否按当前假设推进；阻塞单独列明。修复缺陷是一个带原缺陷 ID 的动作，不自动变成新阶段。不得用“阶段进行中”掩盖阻塞，也不得因存在阻塞就抹掉阶段已经完成的独立交付物。

建议使用下列简明值，并在总 TODO 中保持前后一致：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `phase_status` | `planned` / `in_progress` / `completed` | 当前阶段尚未开始、正在执行或已满足其退出条件 |
| `health` | `on_track` / `at_risk` / `blocked` | 当前计划的推进状态；不代替阶段状态 |
| `blockers` | 项目列表，可为空 | 具体受阻项、owner、所需动作与下一检查点 |

阶段完成只关闭该阶段列出的工作，不表示模块、整体产品或交付已经完成。缺陷修复、返工和新增需求回填到原 ID 或新 ID，并保留其关联关系。

## 2. 总 TODO 的稳定记录

每个任务或交付使用稳定 ID。ID 创建后不因标题、owner、优先级或状态变化而重编号、复用或删除；关闭项保留在历史中。每条至少记录：

- `id`、简短目标与对应的原缺陷／用户需求 ID；
- 交付物及其可定位路径；
- owner、允许写入路径和协作方；
- 前置依赖与当前阶段；
- `phase_status`、`health`、阻塞列表和更新时间；
- 已完成证据、剩余工作及阶段退出条件；
- 估期区间、成立前提和下一检查点；存在未知时记录调查动作、调查 owner 和判断时间。

更新时间只在实际状态、证据、范围或下一步发生变化时更新。已完成内容应写可复核的产物或验证证据；“已看过”“文件数增加”“测试数量较多”不能替代证据。取消或暂缓的事项保留 ID，并记录原因、决策来源和后续条件。

## 3. 阶段推进与修复闭环

整体设计阶段确认用户目标、边界、责任 owner、关键依赖、切片次序、风险、需要的决定以及整体退出条件。模块设计把这些约束落实到本模块的输入输出、实际调用方、公开契约、状态或数据 owner、允许路径和验证场景。设计阶段不替用户决定尚未授权的行为，也不将目标架构当成已经实现的事实。

编码阶段只实现获准范围。报告要区分实现完成、局部验证和跨模块接通。缺陷修复回指原缺陷，先保存修复前的复现条件或失败结果，再记录最小改动、同一场景的修复后结果和相关回归；若修复暴露新缺陷，另建关联 ID，不覆盖原失败记录。

联调阶段使用正式公开入口和实际装配连接 owner。报告真实调用链、双方契约、运行对象和状态权威；测试替身或受控注入要标清其范围，不能冒充默认产品装配或真实外部闭环。联调失败时记录原始可复现症状、定位到的差异、owner 与下一动作，保留失败证据。

验收按已经批准的需求、工程标准和任务退出条件逐项给证据。若没有相应授权或能力，明确列为未完成、拒绝或待决；不得自行降低断言、跳过失败、用数量或单个成功用例替代验收。

交付阶段提供可接收的实际产物、版本或冻结来源、精确变更路径、消费方式、实际执行的命令及结果、未测范围、阻塞 owner 和后续检查点。交付报告应说明代码、安装版、受控对象、默认生产装配及真实闭环分别处于什么状态；不能把其中一种验证扩写成其他层级的结论。

完成用语按实际证据使用：

- **编码完成**：任务范围内的实现和本地检查已完成；跨 owner 接线与整体验收仍可未完成。
- **联调通过**：声明的真实调用链已通过列明的联调场景；不能据此声称默认生产配置或外部全链已通过。
- **交付完成**：本任务获准范围及其退出条件均已满足；任务要求的产物已交给指定接收方，接收方能按交接说明复现并使用，交接信息和证据齐全。未完成的退出条件不能仅靠列入“剩余项”后仍宣称交付完成。模块交付不自动等同产品闭环。

新缺陷或回归必须记录首次发现点、影响、复现／失败证据、修复 owner、原任务关联和修复后同场景结果。若新缺陷要求退回阶段，应记录原阶段→新阶段、回退原因、证据、负责 owner 和下一检查点。修复改变既有行为时，说明依据并由原有决策权限确认，不以静默修改期望值处理。

## 4. 未知、估期与进展报告

已知工作和未知事项分栏记录。未知不能写成“待确认”后长期悬置；每项应有调查动作、负责 owner、需要谁判断，以及明确的检查时间或触发事件。检查点到达仍未知时，更新原因和下一步，不伪造结论。

估期使用区间并写前提，例如依赖 owner 提供接缝、环境可用或回归窗口释放。存在关键未知时，列出未知和可能影响，不报虚假完成百分比或保证日期。发现前提失效、估期将延期或原计划不可实现时，主动报告影响、已做动作、可选处理及需要的决定；不要等被追问。

默认进展摘要控制在一屏内，至少包含：整体阶段、当前阶段健康、这轮完成的主线、剩余风险或阻塞、下一检查点和需要的决定。详细 TODO、逐项证据、命令输出摘要和模块 handoff 通过路径展开。测试、文件、提交或覆盖率数字必须附带范围和证据，不得用数字替代行为结果或完成声明。

每轮进展都按增量说明原问题到本轮结果，明确区分新增工作、缺陷修复和验证动作。修复或缺口验证应尽量复用原失败场景，并报告同场景结果；重复验证需说明触发原因，例如源版本变化、前次失败或新依赖变化。最小记录格式如下：

```yaml
before: 原缺陷、缺口或前一检查点结果及证据
change:
  new_work: 本轮新增工作及对应需求 ID
  fix: 原缺陷 ID、具体修复
  verification: 验证动作及其触发原因
same_scenario_result: 原场景的结果，或说明为何无法复现
validation_layer: source | installed | controlled-host | default-production | real-end-to-end
untested_or_remaining: 未测项与剩余缺口
revalidation_reason: 重复验证时填写触发原因；不适用时为空
```

单个阻塞连续 30 分钟没有实质推进时，报告具体原因、已经尝试的动作及结果、当前影响和需要的决策或协助。报告后继续推进不依赖该决定的工作；不得因此停住整个任务，也不得自行扩大范围绕开阻塞。

## 5. 多 owner 协作与交接

Sol 负责协调顺序、共享边界和串行测试／安装／构建窗口；每个 Luna 或其他执行者领取互不重叠的 owner 与允许路径。交接前先核对共享写权和当前冻结状态。协调者维护依赖关系，不要求各执行者反复全量打包或审计已经稳定的所有目录；先验证真实纵向调用链，只有接近最终发行或交付门槛时才做所需的发行产物验证。

多执行者由 Sol 协调，并遵守仓库 `AGENTS.md` 的并行人数、写权与测试串行限制；当前授权上限为主协调者加最多三个子任务（一个 Sol、两个 Luna）。不递归派生子代理。每位执行者如需报告模型或执行身份，必须使用实际身份，不冒称 Luna 或其他模型。每项任务先分配独占 owner 和允许路径；共享路径需由协调者明确安排顺序。

交接必须让接收者不依赖口头上下文即可继续，最少记录：

- 稳定任务 ID、owner、允许／实际修改路径；
- 实际 source、构建产物或安装产物的版本／manifest／哈希来源；
- 被消费的公开 contract、入口和装配路径；
- 实际命令、退出码、结果与验证对象；
- 未测范围、已知失败、环境前提和阻塞 owner；
- 下一动作、退出条件、预计区间和下一检查点。

明确区分 source 测试、安装版测试、受控宿主／插件选择、默认生产装配、真实外部闭环。声明来源时写清快照、wheel 或安装位置的精确身份；活动源码、历史 receipt、构建产物和安装字节不可互相替代。

若执行过程中发现估期遗漏、超出原范围的缺陷或用户新需求，先记录其来源为原计划漏估、执行中发现的缺陷或用户新增需求，并建立或关联稳定 ID，说明影响与建议处置，再由现有授权方调整总 TODO 和写权。原计划任务仍保留原 ID、原目标和当前状态；不得静默扩大目标、占用他人路径或把新增范围算作原任务已承诺交付。

## 6. 最小总 TODO 模板

```yaml
- id: stable-id
  goal: 本项可复核的目标
  related_to: [original-defect-or-request-id]
  deliverables: [path/to/artifact]
  owner: owner-name
  allowed_paths: [path/or/glob]
  collaborators: []
  dependencies: []
  phase: design | implementation | integration | acceptance | delivery
  phase_status: planned | in_progress | completed
  health: on_track | at_risk | blocked
  completed_evidence: []
  remaining: []
  blockers: []
  exit_criteria: []
  estimate: "区间；前提"
  unknowns:
    - question: 尚未查明的问题
      investigation: 下一项调查动作
      owner: responsible-owner
      decision_by: checkpoint-or-time
  updated_at: "ISO 8601 timestamp"
  next_checkpoint: "具体事件或时间"
```

没有未知时使用空列表；没有阻塞时使用空列表。TODO 模板给出记录字段，不要求无关任务填入虚构依赖或未知。

## 7. 最小 handoff 模板

```markdown
任务 ID / owner：
允许路径 / 实际变更路径：
Source 与构建／安装产物身份：
公开 contract、真实入口与装配：
验证对象及实际命令 / 退出码 / 结果：
未测范围、失败与阻塞 owner：
剩余动作与退出条件：
估期区间及前提：
下一检查点 / 需要的决定：
```

空项写 `无` 或 `未运行` 并说明原因，不省略字段造成范围误读。
