# 会话与分支工作规矩（用户裁定，主会话遵守）

建立：2026-09-28。来源：用户与 plugin 线主会话的流程约定。本文件是这些规矩的唯一记录处；修订由用户裁定后更新。

## 1. 阶段与 1+x 结构

- 持久事实只有 **1+x 分支结构**（core + 各 plugin 分支）。每个实施阶段的 worktree 与会话在阶段收口、改动并回 1+x 之后**销毁**。
- 任何新阶段的起点 = **当时的 1+x 实态**（分支 SHA、目录、账面开工时重新实测），不沿用上一阶段实施树的树内状态，不引用已销毁的会话。
- 并回哪个分支、用什么结构（1 是 core，x 是几支 plugin 分支），由用户按当下状态决定。

## 2. 改已并回的改动 = 新 worktree、新会话

- 凡是针对**已并进主要分支**的改动，一律**开新 worktree、作为新会话的更改**。不存在"给已关闭的会话贴补充说明/补充提示词"这类操作——关掉的会话就是关掉了。
- 提示词只发给**当期活着的**会话。为未来新会话准备的提示词叫**开工提示词**，配合新树的基线配方使用；不叫"补充说明"。

## 3. 主会话职责（plugin 线）

1. 与用户讨论需求；
2. 按 Spec Kit 标准设计隔离的实施方案包（含写入面、接入点矩阵、消费账 api-requests、集成账 integration-request、门与反例）；
3. 选基点开 worktree、把材料放进树里；
4. 给每个新会话一段简短的 `/goal 完成 xxx 文档的所有要求` 开工提示词（细节全在文档）；
5. 用户开会话执行；成果按 1+x 并回；合并后用户回主会话做全局状态分析，循环下一阶段。
- 方案包基线引用一律指向 1+x 结构（main / 各 plugin 分支），不引用兄弟阶段树。

## 4. 命名纪律

- 不用历史线代号（Q1..Q5 / Z1..Z3 / C0）指代域，一律用 `plugins/` 下的**插件目录名**（skills / prompts / command-templates / subagents / mcp / permissions / sandbox / profile / chat / model-provider / harness…）。
- 历史目录名（如 `specs/011-q2-prompts-commands/`）作为路径保留，不在行文中使用代号。

## 5. 其他既定裁定（散件）

- 真实模型调用（E3）未授权一律不跑；受控 fake endpoint 的 E2 允许。
- 方案包派单前过规范核对（`.specify/memory/constitution.md`）+ 越界自查 + 关键 file:line 引用抽验。
- 六大类资源处理机制的优先顺序：指令与人格（=prompts 域，已裁八家）→ 运行偏好 → Hooks/可执行扩展 → LSP/搜索（先侦察支持面）；effort/预算/超时并入 model-provider 域后续批次。
