# Ordessa 首个开箱即用发行版：短期任务与交接

状态：**规划 / 未开工**。记录于 2026-09-28，基线 `main@78afe8c644`。本文件是短期产品目标与接手入口，不代表任何发行门已经通过；不授权 push、发布或真实模型调用。

## 目标与首版边界

目标不是再启动一套开发预览，而是交付一个普通用户可安装、首次打开即可开始使用的 Ordessa。建议首版平台先限定 **Ubuntu/Linux x64**；其他系统、自动更新和 Skill 驱动工作系统留待后续版本。首版至少要让用户完成“安装 → 打开 → 选择/配置 Harness → 选择项目 → 新建会话 → 对话 → 退出重开后找回历史”。Pi、Codex、Claude Code 是此前讨论的首版 Harness 目标；应按同一门逐个验证，不得把仅有配置形状、假对端通过或桥级握手称为可用。

没有显式指定数据位置时，应用应自行创建和复用用户级 `~/.ordessa`，**不是仓库内目录，也不是临时目录**。启动不要求用户手填 `ORDESSA_SERVER_ORIGIN`、令牌、端口、Python/Go/Node 路径、ACP 桥路径或 `--data-root`。显式位置覆盖可作为高级/开发入口保留。已有数据绝不自动从旧根导入；升级/迁移须有备份、兼容检查与可理解的失败提示。

首版基本交互范围建议包含项目与会话、文本双轮、历史恢复、基本的 Harness/Profile/provider/model 选择、斜杠命令和附件入口；其中 Profile、模型切换、命令与附件须在真实接缝完成后才算入发行验收。若发行范围需要再缩，先由用户裁定并更新此文档，不能由执行者默默降级。更复杂的工作系统、MCP/Subagents 全能力和跨系统发行不阻塞这一版。

## 已核实的现状与风险

| 事实（本轮源码/报告核对） | 对发行的影响 |
| --- | --- |
| `apps/server/src/ordessa_server/__main__.py` 的 `--data-root` 仍为必填；Server 可在给定根后运行，但没有默认用户级根。 | 首启不能让用户自己建立数据根或写命令。 |
| `apps/desktop/electron/main.ts` 发现扩展、创建窗口，却不启动/监管 Server；开发脚本使用临时 userData。 | Desktop 必须拥有随包 Server 的生命周期、就绪检查与故障 UI。 |
| `products/desktop/extensions.json` 启用的是 `agent-*` 旧链；新 Chat 不在默认启用清单。 | 包存在不等于产品已装配，必须验证最终启用面。 |
| `specs/011-z1-profile/report.md`、`specs/011-z2-chat/report.md`、`specs/011-z3-model-provider/report.md` 都登记了 PARTIAL 或未验证的真实接缝。 | 不得沿用各包局部门禁替代发行物端到端验收。 |
| 目前没有经验证的安装产物与“干净机器首启”证据。 | `npm run dev` / Electron smoke 不能作为发行绿灯。 |

上一轮在**临时数据根**做过无模型 native Pi 预检，证明部分桥/Server 通路可运行；这不是正式用户数据，也不是产品级或真实模型的三 Harness 验收。当前不要求手工创建 `~/.ordessa`，应由实现完成自动创建与安全检查。

## 实施顺序（Spec Kit 方案包，先依赖后并行）

1. **冻结发行规格与矩阵**：在一份 Spec Kit 方案中明确安装平台、每条用户旅程、三品牌能力矩阵、错误/恢复语义、数据兼容及不在范围的功能。当前文档是 handoff，不替代详细 `spec.md`、`plan.md`、`tasks.md` 与验收 checklist。产品语义未定时不得让实施者自行裁决。
2. **产品启动纵切**：在产品/launcher 层实现默认数据根解析、安全创建与复用，随发行物启动自有 Server，取得随机 loopback origin/令牌，等待就绪后再交给连接器；退出只停自己启动的进程。`apps/server` 保持通用宿主；若 headless CLI 也支持缺省数据根，两入口须有同一个明文规范和一致性测试。
3. **Pi 完整路径先通**：默认产品装配 → 项目 → ACP 通道 → 会话首轮与下一轮 → 退出重开找回历史。用受控对端完成无费用回归；真实模型调用另行取得用户对范围/费用的批准。此阶段暴露“空窗口、选连接”或旧执行入口缺文件时必须判红。
4. **同门扩展 Codex/Claude Code 与 UI 基础能力**：逐品牌做进程配置隔离、provider/model 应用与会话继续；接入 Profile、Chat、命令、附件的真实服务与默认产品清单。品牌专有逻辑留在 Harness 适配，业务规则留在插件，禁止为了装配把业务塞回 Server/Desktop 宿主。
5. **发行物与干净环境验收**：构建 Linux 安装包并包含固定版本的 Desktop、Server Python 运行时与依赖、ACP 桥、插件和许可证资料；在无仓库、无开发工具链的干净用户环境安装运行。锁定版本与哈希，给出版本/日志/恢复入口。正式发行不得沿用开发脚本的 `--no-sandbox`。发布与推送仍须用户明确授权。

可并行的仅是**契约/文件所有权不重叠、能独立验证**的工作；启动器与产品装配、Chat 与接缝、三品牌支持各自有先后依赖。现有 `main` 有其他会话留下的未提交任务文档，接手者必须先检查状态、保留它们，再提出工作树划分；本 handoff 不自动开树或改分支。

## 发行门（缺席即红，不以局部测试代替）

| 门 | 正向验收 | 必须抓到的反例 / 缺席处理 |
| --- | --- | --- |
| F1 首次启动 | 干净 HOME 安装后双击启动；自动创建权限合适的 `~/.ordessa`，Server 就绪，界面可继续。 | 无目录、端口冲突、缺随包二进制、数据根被锁/不可写时显示可操作错误；绝不空白或假绿。 |
| F2 基础对话 | 每个承诺 Harness 分别完成项目选择、两轮会话、正确结束和重启后的历史。 | 未安装/未登录/适配器失败时诚实不可用；桥握手或 fake-only 不算真实可用。 |
| F3 配置与输入 | Profile 和 provider/model 切换遵守会话边界；命令与附件经真实接缝生效。 | 仅有 UI 控件、仅能保存数据、或者失败后静默回退，均判红。 |
| F4 数据与安全 | 新根/已有根/升级失败均保全数据；令牌不进渲染进程；只接受 loopback；正式 renderer 沙箱开启。 | 缺备份、错误进程被关闭、凭据泄漏或 sandbox 关闭均判红。 |
| F5 发行物 | 直接安装打包产物，无 Node/Go/仓库 `.venv` 依赖；重装/升级后仍能启动。 | 只能从源码跑、依赖开发机器 PATH、缺少许可证/资源或不能重启均判红。 |

验收记录须写明构建 SHA、安装包哈希、系统环境、实测命令/截图、通过数与失败 ID；任何尚未执行的门标 **未验证**。已登记的仓库红账本仍需逐 ID 比对，不能用“测试数量差不多”代替。
