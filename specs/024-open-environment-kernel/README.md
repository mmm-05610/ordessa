# 开放 Agent 工作环境：内核建模、攻击与重构设计

日期：2026-10-03。状态：任务要求已建立，模型未定稿，未授权生产实现。

## 1. 目标与交付边界

设计一套能够容纳 Agent 与第三方工具工作的可扩展后端环境，并提出现有后端向它收敛的重构方案。
不是能力调用网关，不逐项复制 Harness 原生功能，也不是只把目录搬到一起。

本任务执行顺序：现状盘点 → 能力边界 → V1 模型 → 多代理攻击 → V2 修订 → 再攻击 → 候选模型与重构实施包。
本任务不直接实施重构。设计中的重大语义、安全边界或数据迁移选择必须向用户提出，不能自行当作批准。

只写本目录内的设计、攻击记录、进度与离线验证材料。源码、现有运行数据及其他 specs 只读。
不启动/关闭/重启服务，不调用真实模型，不读取 key.txt 或登录令牌，不安装资产，不修改 AGENTS.md。
不新建 worktree，不切分支，不提交/合并/推送。本任务不更新云端；用户自建网站的编辑接口尚未提供。

## 2. 用户确定的方向

1. Ordessa 更像一套开放、可扩展的 Agent 工作环境，尽可能把参与者完整装入，而不是抽取几个功能接线。
2. 内核不理解 ACP、Codex 等具体外部服务。接入者声明交给环境管理的范围，保留自己的内部机制。
3. 原生能力优先保留。上游通过已承载的交互入口新增命令时，应无需修改核心或为该功能新建专用 API。
4. 装入的组件可以移除；系统与其他独立组件继续工作，历史与未解决事实不得损坏或虚构完成。
5. 一套后端运行权威，不保留 Server 宿主与 Pacthold 相互平行的插件/执行中心。
6. 经内核暴露的能力调用使用统一执行语义；管理、持久化、租约、恢复不能简单绑成不可分割的重成本。
7. 顶层 packages/frontend 与 packages/backend 是包组；内部可以拆职责清晰的独立包。包数和旧目录不决定模型。
8. 不接管原生模型推理、工具调度、压缩或工作流等内部事务。可选增强不能成为原生使用的唯一入口。

此前 Provider/Capability/Ref/Binding/Execution/Object/Lease 及“前端7包、后端4包”只是讨论稿，不能作为冻结合同。
如果实证表明概念需拆分、合并或重新定义，应写出原因、反例及迁移影响，而不是维护命名。

## 3. 能力边界草案：先审查再冻结

### 环境应当支持

- 安装/发现/启用与运行实例分离；表达来源、版本、依赖、兼容要求及缺失状态。内核不充当网络包管理器。
- 插件与外部参与者明确区分；一个插件可以承载多个独立实例，提供多个能力或适配多种外部服务。
- 短操作、持续活动、后台工作、异步结果、双向交互、数据流；不能把它们误当同一种结束条件。
- 工作上下文及资源关联：工作区、配置引用、身份引用；敏感内容与业务状态仍归其所有者。
- 能力贡献与消费、扩展点、嵌套/组合调用、顺序与依赖、必要并发控制；不预设 Agent 协作业务。
- 引用、绑定、共享、借用、持有与销毁责任；托管对象、操作执行与观察记录分别解释。
- 取消、超时、失联、部分失败、未知结果、核对、恢复与清理；不靠猜测建立事实。
- 同一套内核语义可从本地/CLI/网络入口调用；网络鉴权与协议实现独立，但不得另造运行权威。
- 可观测与可追踪；内存记录和持久事实区分，流量不必全量持久化。
- 平滑加入、移除、重新启用与升级；活动期间替换是否允许及如何处理必须有明确定义。

### 不自动纳入

- 外部服务内部的会话状态机、推理、工具审批规则、workflow、记忆或模型调度。
- 内核内置 ACP/品牌判断、必需 Profile、业务目录枚举，以及重新实现第三方能力。
- 默认授予系统权限、隐式登录/重连/重发、内核自行制定业务安全策略。
- 外部副作用严格 exactly-once、分布式共识/集群调度、通用工作流 DSL。

远端服务可以通过适配者承载，不等于第一版内核必须分布式部署。信任与授权检查必须可承载，但不因此造新 sandbox。
遇到超出边界却确实必要的能力，提出裁决，不默默扩展范围或把反例踢出范围。

## 5. 每版模型必须回答的问题

1. 环境里的参与者是什么？插件、安装单元、运行实例、能力提供者是否等价？
2. 一次活动的身份、开始/结束、输入/输出、取消和未知证据分别是什么？
3. Execution 与长寿命对象、原生会话、流连接如何关联？不能靠同名 Execution 掩盖差异。
4. Ref 指什么？Binding 固定什么？使用权与所有权怎样表达？悬空、过期及跨实例引用如何拒绝？
5. 普通查询如何统一管理而不必持久化？内核自身记账/核对是否产生无限递归 Execution？
6. 谁是每种状态的唯一权威？提供者报告矛盾、晚到或乱序结果时如何处理？
7. 实例、操作和订阅的存续是否依赖客户端连接？共享使用者退出时谁可停止对象？
8. 插件升级、卸载、重启后的版本/代际如何识别？旧句柄不能意外控制新实例。
9. 未知原生命令与事件如何承载？安全封装、展示降级、背压与未知业务语义如何共存？
10. 什么保证是基础要求，什么需要声明/协商？缺少恢复证据时应如何明确降级？

每个概念提供：中文定义、非例、身份作用域、状态/关系规则、合法与非法事件序列。
先给非专家可读的图与例子，再给形式化契约；不要只有术语列表或漂亮目录树。

## 6. 多代理攻击工作法

主会话是唯一模型修订者与账本作者。用户已明确授权本任务多子代理审查。
最多3个攻击子代理同时工作，不再嵌套派代理；子代理不写生产源码、不做 Git 写操作。
每次给代理自包含的版本快照、边界、任务和返回格式，不让它依赖整段聊天历史。

三个独立方向：
- A：语义与组合。攻击参与者/实例/执行/对象的区分、绑定变化、嵌套执行、共享、循环依赖与并发。
- B：故障与安全。攻击崩溃窗口、未知结果、取消竞态、陈旧句柄、越权引用、卸载与升级、清理失败。
- C：开放环境与可接入性。用不同参与者接入，攻击过度抽象、品牌知识泄漏、网关化、原生能力丢失。

攻击结果格式：编号/严重度/模型版本/边界条目/前置条件/事件序列/矛盾或危险/应满足不变量/修复建议。
不接受“感觉复杂”“建议增强”等无反例评价。作者必须逐项处置，不能只写已考虑。
代理建议是待核对输入，不是用户裁决，也不是形式证明。

至少两轮：V1并行攻击 → 处置并形成V2 → 再攻击V2。可继续V3及后续，但每轮须有新增实质进展。
后续攻击轮换题目/视角，并安排至少一个未参与最终模型编写的复查者；不只复述第一轮已知问题。
若连续两轮无法消除同一重大矛盾，立即提交给用户讨论，不无限调用代理；不以预算将耗尽冒充通过。
不无人值守轮询；本任务是有明确交付条件的设计工作，不自动安排定时任务。

## 7. 必须覆盖的反例与接入样例

至少覆盖以下20组，每组给出期望结果及可执行离线检查或未来测试条件：
1. 空产品、无Harness、无Profile，内核仍可启动；缺依赖拒绝半激活。
2. 同插件承载两个实例，其中一个退出不影响另一个。
3. 创建操作结束后，对象仍存续；客户端断开不等于对象结束。
4. 原生长会话承载多个消息轮次，环境不镜像原生内部状态机。
5. 上游新增未知 /workflow，既有原生入口可达，无需核心功能枚举与专用API。
6. 该能力只存在未承载的原生UI：明确适配缺口，不能假报零适配自动可用。
7. 未知事件/输出保留与展示降级，不错误解释为审批或执行终态。
8. 流式背压、订阅断开、晚到事件、重复事件、无限流与资源上限。
9. 查询通过统一活动机制，但不强制数据库写入/租约获取；记账不无限递归。
10. 重复请求，同键同输入及同键异输入分别处理。
11. 外部已生效、回执丢失；进程分别在意图写入前后、调用前后、结果落盘前后崩溃。
12. 取消与完成同时到达；请求取消、确认取消与超时不混同。
13. 重启恢复只能依据证据；无查询能力时保留未知，不盲目重发。
14. 共享对象多个Lease，其中一个释放不销毁其他使用者的对象。
15. 持有者消失、对象失联、过期Ref、旧代际句柄和跨作用域引用。
16. 嵌套执行、组合部分成功、主因与清理失败同时发生，不承诺外部事务原子性。
17. 激活/贡献冲突或失败回滚；正在被使用的插件卸载、升级与能力撤销。
18. 配置更新仅作用于声明允许的范围，不偷偷修改进行中的活动。
19. 插件移除后历史可读且缺实现可见；重新安装不冒认旧活动。
20. HTTP/CLI/本地入口调用同一能力，不产生三套状态权威。

接入样例至少包括：原生Agent（如Codex）、持续第三方工具服务（如MCP）、普通资源业务（如Skills）、
短暂外部命令及后台长期工具。只做纸面/离线受控模拟，不运行真实资产或模型。
各样例交付安装→实例化→交互→更新→移除的完整过程，写明插件和核心各做什么。

## 8. 重构设计要求

模型收敛后才提出目标子包；不要先按“后端4包”硬塞功能。
每个包给出公共接口、所有状态、允许依赖、禁止依赖、独立验证方式及源码迁移映射。
对当前新旧机制逐项选保留/合并/适配/退役，说明证据；优先复用可靠实现，不照新模型重写一遍。
兼容入口可以暂留，但不能维持两套权威状态；双写不是统一。
明确持久标识、旧数据读取、迁移失败、回滚以及原生资产/适配接口的影响。
分阶段计划必须包含每阶段行为不变量、基线回归、正反例、缺席行为与回滚点。
将必须改动的产品调用接缝列清楚，不许宣称“全部只在Pacthold内部”掩盖外部语义变化。
前端只列受影响契约，不实施UI重构；两套环境不要求使用完全对称的实体模型。

## 9. 文档产出与收口条件

所有产出在本目录：
- status.md：当前版本、完成/进行中/阻塞、下一步、用户待决项、代理轮次与可取得的用量。
- inventory.md：现状、消费者、重叠机制与证据。

- models/vN.md：每轮完整模型、图、接入例子和版本差异。
- attacks/round-N.md：原始攻击、逐项处置、复查证据；不能覆盖历史缺陷。
- scenarios.md：场景和预期结果，覆盖矩阵；离线脚本可放 checks/。
- refactor-plan.md：目标包结构、复用/迁移映射、兼容、阶段与验收/回滚。
- review.md：最终候选版本、仍存限制、实施前必须由用户裁定的选择。

可交审核的条件：
1. 能力边界和所有权明确，至少两轮实质攻击均有记录。
2. 无未解决的阻塞性模型矛盾；所有严重问题有可核对的处置，不靠重新标低优先级过门。
3. 上述样例可以完整接入，不依赖品牌特判、绕过内核或平行宿主。
4. 原生新增能力与移除组件两个核心场景有明确保证和限制。
5. 最终候选经独立复查；未运行的测试明确标为设计验收条件，纸面推演不叫实机通过。
6. 给用户一屏结论及文档指针，不声称生产重构完成，也不承诺模型已被绝对证明。

若缺少用户裁决，整理选项/建议/代价后交回；继续完成无关设计工作，不擅自实施。
