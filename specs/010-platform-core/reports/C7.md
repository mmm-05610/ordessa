### Mechanisms reused (verified against the current tree, not assumed)

- **Resource scope**: `packages/desktop-platform/extension-api/src/index.ts` — `OwnedResources` is the
  host-issued `ResourceScope` (`{ isDisposed, add }`); `add` on a closed scope disposes the incoming item
  and throws `Resource scope is closed`; `dispose()` is idempotent, walks in reverse and aggregates
  cleanup errors. C7 registers/binds through this object and takes ownership **from the scope identity**,
  never from a caller-supplied owner string (contract §2). No second scheduler, no replacement scope.
- **Service DI + lifecycle**: `extension-host/src/runtime.ts` — `runtime(plugins)` with
  `provides`/`requires`/`autoStart`, duplicate id and duplicate provider rejection, per-plugin
  `registered/starting/active/stopped/failed` snapshot, activation-failure resource rollback
  (`AggregateError` on cleanup), `failures[]` for the renderer's `role="alert"` output. The UI service is
  one ordinary plugin here; a consumer `requires` the neutral `UiComponentsToken`, never a concrete
  provider, so provider unmount cannot drag a consumer down (contract §1).
- **Snapshot/subscribe precedent**: `extension-api/src/contributions.ts` (`Contributions<T>`) — stable
  sorted snapshot array + `Signal` + `DisposableDelegate`, the shape C7's binding must stay compatible
  with `useSyncExternalStore` (contract §3: unchanged snapshot keeps object identity).
- **Shared single-instance carrier**: `@extensions/ordessa.contracts/contract.js` re-exports
  commands + Workbench api + Connections api, and now the C7 api
  (`packages/desktop-platform/contracts/foundation/src/contract.ts`). Extension bundles externalise
  `@ordessa/extension-api` and read shared types only through that carrier, which is what makes the Token
  and the key/registration brands single-instance in a real build (UI-12).
- **Real-build machinery**: `tooling/build-all.mjs` (discovery roots
  `contracts`, `connections`, `packages/workbench`, `plugins`; writes
  `products/desktop/dist` + `extensions.lock.json`), `tooling/build-extension.mjs` (esbuild +
  `splitting`, `// <source>` banners), variant seams `ORDESSA_PRODUCT_MANIFEST` /
  `ORDESSA_PRODUCT_OUTPUT_ROOT`, cross-process `tooling/real-build-lock.mjs`, watchlist scanners and
  `TOKEN_/KIND_SOURCE_DISCOVERY_ROOTS` in `packages/workbench/tests/token-scan.mjs`, dev-time alias map
  `tooling/vitest-extensions.mjs`, and the five temporary-Electron gates driven by
  `apps/desktop/scripts/*.mjs` with isolated `userData`.
- **Product assembly**: `apps/desktop/renderer/main.tsx` renders an empty host first
  (`runtime([])`), then `runtime(loaded.plugins)` from `loadExtensions(catalog)` where
  `catalog = window.extensionCatalog.read()` (Electron main, `ORDESSA_EMPTY_HOST=1` for the empty-host
  build); enabled ids are product data in `products/desktop/extensions.json` (+ `extensions.foundations.json`).

### Two placement decisions, recorded because the contract leaves them to this line

1. **Where `createUiComponentsPlugin(selection)` is called** (contract §24 "具体文件落点按当前 C 代码
   确定"): the selection is *product data*, so it enters through the existing product data channel —
   `products/desktop/extensions.json` gains an optional `uiComponents` selection array which the
   main-process catalog forwards, and the renderer's product assembly turns a **non-empty** selection into
   the service plugin returned by `createUiComponentsPlugin` and appends it to the same
   `runtime(plugins)` array. Consequences kept honest: an empty/absent selection adds nothing (empty host
   and the default product keep their exact current startup, plan line 37/39), the renderer stays
   domain-neutral (it passes opaque strings through), and a provider can neither `setDefault()` nor
   out-order another provider, because the table is assembled before activation.
2. **No cross-host registry**: the `(id, major) → key object identity` table lives in the service
   instance created per assembly, and is dropped when that host is destroyed (contract §2 last
   paragraph). U07 (two hosts independent) is therefore testable, and a module-level global map is
   explicitly not allowed.

`products/desktop/tests/ui-components-platform.test.mjs` (3 IDs, exit 0) adds the
build/source level proofs: no controlled fixture name is branched on anywhere in
`packages/desktop-platform/**` (V05/U16 — a new kind costs extension + product
config only); across the built example bundles the test-domain key is constructed
**exactly once**, in its own carrier, with zero copies in provider and consumer, and
no bundle carries a private React copy while the consumer still imports React

neither the service nor any provider, while importing the **built platform carrier**
yields `UiComponentsToken` (`ordessa.ui-components.v1`), `defineUiComponent`,
`registration` and `UiComponentsError` with `createUiComponentsService`,
`createUiComponentsPlugin` and `ComponentOutlet` all absent — the API is usable with
no implementation present and importing it activates nothing (UI-01/UI-14).

One cross-bundle identity fix came out of this: the binding capability symbol is
`Symbol.for('ordessa.ui-components.binding-internals')`, because the service, the
provider and the consumer are three separately built bundles that each carry their
own copy of the internal module — a plain `Symbol(...)` would give each copy a
different identity and the consumer's outlet could never resolve a binding the
service created. It stays an identity marker, not a registry: the capability still
travels with the binding object.

### T034 — how the UI service actually assembles (landed with this checkpoint)

The contract left the file placement to this line, and the carrier identity rule
decided it: Lumino matches services by **Token object identity**, and consumers
reach the carrier copy through `@extensions/ordessa.contracts/contract.js`, so the
provider must be an extension bundle too. A renderer-side plugin would have bundled
a second `new Token('ordessa.ui-components.v1')` — precisely the CN-08 defect class.

- `assembly/entry.ts` — `createUiComponentsPlugin(selection, token)` returns
  `{ plugin, inspectRequirements }` exactly as the contract promises; the plugin is
  an ordinary Lumino service plugin (`id: ordessa.ui-components`, `autoStart`,
  `provides: token`) whose activation only registers the service with the host
  plugin scope, so a failed activation or deactivation reclaims everything.
  `parseUiSelection` accepts only generic `{componentId, major, providerId}` rows and
  treats an absent configuration as *no selection* — an empty product stays empty.
- `extension/entry.ts` + `manifest.json` + `build.mjs` + `ordessa.id` — the built-in
  extension, enabled by the product by id; it imports the Token from the shared
  carrier and the implementation from `../src`, so the bundle itself constructs no
  Token. That required splitting the error type into the Token-free
  `api/errors.ts` leaf: `src/index.ts` used to value-import `UiComponentsError` from
  the module that constructs the Token, which would have copied the Token into the
  extension bundle.
- Product configuration reaches it generically: `discover` accepts an optional
  `config` map keyed by extension id (validated as ids only, forwarded opaquely,
  malformed map fails closed) and `loadExtensions` passes it as the entry factory's
  second argument. The host never reads the value, so no component name appears in
  host code. Three new host IDs in `loader.test.ts` cover forwarding, omission when
  unset, fail-closed rejection, and the factory argument.
- Required-binding diagnostics: `apps/desktop/renderer/main.tsx` asks each loaded
  plugin for the optional generic `inspectRequirements()` after activation and
  renders the result through the existing `role="alert"` path — generic capability
  probe, no domain branching, and nothing appears for a product that does not use
  the service.
- The default product manifest is unchanged (the service is not enabled there), so
  startup behavior of the shipping product and of the empty host is untouched (U15/V08).

Evidence at this checkpoint: `npm run typecheck` exit 0; `apps/desktop` 39/39 exit 0
