### Contract decisions (each pinned by a test)

1. **Payload stays opaque at this layer.** No pacthold import, no payload validation — the zero-dependency gate is a real sentinel test (`test_zero_dependency.py`: import-hook assertion + planted-stub markers never reached + a self-check that the planted mechanism does record a genuine `import pacthold`). C1 types are consumed only by the T015 binding in `apps/server`.
2. **Owner is never author-declared.** `Contribution` has no owner field; `stage/commit/rollback` take the host's owner parameter (mirrors C1 `CoreRuntime.stage(owner, contributions)`).
3. **No half-batch visibility.** `stage` prepares without publishing; `resolve()` answers `AbsentContribution` for every point while the batch is staged, and only committed payloads are published, exactly once, in batch order (FR-005).
4. **Rollback after commit is a typed refusal** (`ContributionRollbackRefusedError`), not a silent un-publish: a published batch retires through the host's unregister path.
5. **Required vs optional absence.** `required` without payload, or a host-named required point the batch does not carry, refuses the whole batch (`RequiredContributionMissingError`); an optional missing point resolves to an observable `AbsentContribution` — never an error, never a `None` the consumer has to guess.
6. **Point exclusivity is declared, not guessed.** A duplicate point inside one batch raises `DuplicateContributionError` unless the batch names that point in `open_points` (multi-entry points are an explicit author declaration; the registry/conflict semantics remain the host's T013 job).
7. **Cleanup carries, never swallows and never replaces** (the review round that reworked the first draft, FR-007): a failed staging rolls back **every** already-staged entry in reverse order; a rollback that raises is recorded as `ContributionCleanupError(owner, point_id, cause)` and attached to the in-flight exception's `cleanup_errors` (accumulating, `(AttributeError, TypeError)` tolerated so an attribute-refusing exception propagates unchanged), mirroring `plugin_host/host.py::_carry_cleanup_errors`. `StagedBatch.rollback()` uses the same rule directly: with no exception in flight the failures surface as one `ContributionBatchCleanupError` after every entry has been attempted, and the batch still ends `rolled-back` (idempotent afterwards). The original draft's silent `except Exception: pass` is gone.

### S1c design input read from A's published tree (2026-09-27, `git show b47b6d7803:` only — nothing merged yet)

- **The part that will bite if it is not stated now:** with a store injected, `_write_lock` becomes a **fresh `threading.RLock()` per repository instance** (`:144, :147`), whereas the global path shares `db.write_lock` process-wide. Today `plugins/server-compat/.../execution/sidecar_backend.py:201` builds `CoreRepository()` into live `WorkService`/`ExecutionService`, and any additional repository (tests, a second service, a future per-plugin repository) currently serialises against it through that shared global lock. After S1c injects, two repositories over the same file no longer serialise in-process — correctness would rest on SQLite alone, and `with self._write_lock, conn:` around multi-statement writes is exactly the code that assumed one lock per database. So S1c is not "pass the connection and delete the pin": the composition must inject **one shared connection provider plus one shared lock**, or the injection silently weakens write serialization. A's docstring promises only "statements run on the injected instance connection", which is true and narrower than what B needs.
- Recorded as a question for S1c's dispatch, deliberately not answered here: whether the shared-lock bridge belongs in the Server's composition (B owns the callable and the lock it hands to every `CoreRepository` it builds) or in `pacthold.work_core` (A's file, which B may not edit while A's lane is under review). The honest default is B-side — inject the *same* connection object into every repository in the round, since `isinstance(store, sqlite3.Connection)` gives them one provider, and a single shared `Connection` makes the per-instance RLock irrelevant because sqlite3's own serialization plus one transaction-at-a-time connection holds. That must be proven by a counterexample test in S1c (two repositories, same injected connection, concurrent multi-statement write → no interleaved partial state), not asserted.
