## Z2 Chat API revision request before C0 consumption (historical audit)

Read-only review of fixed publication `54ad26c15d8480823374d85590919ba6bcca60d2` found three concrete `plugins/chat/api` blockers. C0 requests a Z2-owned `chat-api-r2` checkpoint, with the same public slot IDs and a documented compatibility relation to the first publication:

1. `ChatComponentKey` in `plugins/chat/api/src/contract.ts` uses a private brand distinct from C7 `UiComponentKey` in `packages/desktop-platform/ui-components/api/ui-components.ts`; runtime `{id, major}` equality is insufficient because C7 rejects distinct key objects for the same id/major and TypeScript rejects the brands. `ChatContributionView` exposes only `keyId/keyMajor`, so C0 cannot pass a registered Chat contribution to C7 binding without an unsafe cast or fabricated key. Construct Chat keys through the C7 public factory, preserve object identity in the view, and provide a compile-time/registration counterexample. This is an API package fix; C0 will not alter the owner package in place.
2. `plugins/chat/api/src/registry.ts` shares a single mutable `SourceRecord.entries/state` across independent `queryInputSources` calls. A slow query A for session A can resolve after faster B for session B and overwrite every live view with A's location-specific actions; aborting A can also set B's state. Give each request/view its own generation/result state, and prove the A/B out-of-order resolution and cancellation cases against the same source.
3. The registry freezes only the outer record and retains a caller-mutable `descriptor` (`registry.ts` around registration and scope disposal). Mutating `descriptor.id` after registration makes `scope.dispose()` miss the contribution, leaving it visible. Snapshot/freeze the descriptor identity before indexing and add a mutation→dispose counterexample.

The read-only review extracted the fixed publication to `/tmp/ordessa-chat-api-review`. Its `tsc` counterexample exited 2 with TS2741 for the branded key; a bundled runtime replay printed `after B ['B']` then `after stale A ['A']`, and descriptor mutation left `sample.body` visible after disposal. These are API package defects, not C0 permissions to edit Z2's source.

## Z1 Profile API revision request before C0 consumption

Its checkpoint currently sets `planAnchorRef` to the moving `refs/heads/codex/011-z1-profile`; the common checkpoint contract uses the frozen `refs/heads/codex/011-plugin-plan` design anchor. The implementation SHA is an ancestor, but publication metadata needs a stable anchor in a new `profile-api-r2` record.

The TypeScript `plugins/profile/api/src/contract.ts` models `ComponentKey<P>` as a branded string, while integrated C7 `UiComponentKey<P>` is a frozen `{id, major}` object with private brand and identity registration. C0 cannot bind Profile editor/settings contributions to C7 without unsafe casts or creating a second key object. In `plugins/profile/api/src/contributions.ts`, returned disposables are not added to the supplied `UiScope` and disposed scopes can register new entries; `OwnedResources.dispose()` therefore does not revoke the Profile contribution. Add scope-owned registration and a negative lifecycle test. Until the Z1 revision is verified, this READY record is observed but unmerged.
