Zero-side-effect measurement: every scenario asserts `channel.transport.sent`,

Outcomes per scenario (all PASS):

   fences raise CAPABILITY_UNSUPPORTED, the real adapter answers
   refused/CAPABILITY_UNSUPPORTED, `ready` is False, the prompt frame is refused
   and the recorder is empty. Fail-closed, not permissive.
2. hard deny (signed ceiling `deny read` + a user intent that allows read): the
   host fence raises PluginAdmissionRefused("POLICY_CEILING_VIOLATION") from
   this lane's ruling (the port was consulted: calls == ["submission"]), the
   prompt frame is refused, recorder empty, no approval and no grant written.
3. the same coded denial measured THROUGH the public port adapter comes back as
   `unknown` with code None — the G2 consequence, pinned as a test rather than
   argued.
4. ask: submission with no approval yet => APPROVAL_RESULT_UNKNOWN, the reason
   carries the approval id, a real open fact is recorded (exactly one), the
   prompt is refused and the recorder is empty. Then allow WITHOUT the native
   receipt => the permission fence answers not-True, the host raises
   AUTHORIZATION_REFUSED, grant usage rows 0, nothing relayed; after
   record_native_receipt(confirmed) the same answer is accepted, relayed once,
   and the second copy of the same frame is refused ("already consumed"),
   grant usage 1.
5. forged interaction id (never minted) and cross-run identity ("some-other-
   native-request") and an option contradicting the recorded verdict ("deny" on
   a settled allow): each makes the authority answer False so the host raises
   "permission verifier refused", each leaves grant_fields(...)["consumed"]
   False and grant usage 0 and the recorder empty. The honest answer still
   works afterwards.
6. full chain with the composition's permit record injected: intent-allowed
   prompt admitted -> relayed once -> the same prompt frame refused (one-use rpc
   id) -> Agent asks -> user allow + confirmed receipt -> authorize_permission
