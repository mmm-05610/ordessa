# M05 · 单元选择与配置提案

## 职责
已通过任务准入后，决定是否委派、采用哪个已有单元/上下文或哪份外部组合器提供的配置方案。
只返回提案；不产生/恢复实例、不修改Profile、不预约、不真正等待、不使用通道。
依赖M01、M02网关、外部候选/组合/校验端口；无Ordessa/品牌导入。

## 默认七种动作
| 动作 | 必需依据 | 不允许的捷径 |
| --- | --- | --- |
| noDelegation | 主Agent在已明确范围内处理即可 | 每任务默认外置 |
| continue | 当前节点、原生上下文、权限与占用都适用 | 同标题等于同上下文 |
| reuse | 已存在可用单元、上下文要求相容 | 用其他会话冒充延续 |
| restore | 有原生绑定、公开恢复能力及可核查前置 | 未知恢复时新建替代 |
| wait | 匹配单元暂忙、等待条件/截止时间明确 | 自动轮询或预定占用 |
| reconfigure | 目标、owner配置版本、合法提案、模式明确 | 模型高分覆盖忙碌/共享限制 |
| create | 固定Harness/Profile方案、目录/资源/安装前置和公开只读评估 | 空/权限过滤目录就新建 |

顺序是默认少扰动策略，不是固定调用七次Jev；外部policy可明确改变优先级。
模型只排序硬约束已通过的候选，不覆盖失败/未知条件。

## 硬约束与软排序
身份、版本、namespace、范围、权限、上下文、占用、配置动作/scope/mode、
资源可读性、安装及校验能力是必须具名检查的约束。
其中决定当前提案语义可行性的条件必须有观测；变化频繁的可用性仍作为应用前MUST checker，
不能因决策时检查过就免除应用端检查。缺失必须语义校验时不ready。
软排序包含有依据的适配度、上下文保留、费用/延时、扰动和用户偏好；未知成本不当0。
评分/概率不是所有者声明，也不证明真实质量；并列、低确定性走policy指定分支。

## 外部组合器
ProposalSource只接任务引用、候选引用、配置描述、约束和安全反馈，返回有界完整方案。
由了解配置语义的可信业务组件实现；通用引擎/Jev不枚举字段，也不做无界笛卡尔积。
初版参考组合器使用已有Profile/注册模板和明确允许选项生成最多8份方案；
新增配置kind的解释由外部处理器/schema/owner负责，不在引擎追加if品牌分支。
默认每页32、总候选64、最多4页、组合64上限、每次最多8份、最多2次修正；
最终取全局RunLimits与policy限制的较小值。

不是所有描述都能自动生成合法组合。描述缺少候选选项、兼容规则或语义评估时，
组合器应报告缺口；不宣称JSON Schema足够表达全部配置含义。
required未知/不支持阻止提案通过；optional也不能自动丢弃，除非原任务明确允许。
候选截断时可选“已评估集合中可行方案”，不得宣称全局最优或系统无解；
如果policy要求全目录查尽才create，则complete=false阻止create。

## 判断流程
读取完整性声明的候选 → 硬约束过滤 → 编译有限Choice/Score/Noul问题 →
选择候选ID → 从可信映射取提案 → 外部只读校验 →
valid返回ready，invalid具名可修正反馈交外部组合器产生新方案，
unknown补相关新观测或返回clarify；明确无能力满足才blocked。
端口故障为技术failed，预算耗尽单独终态；不能把它们混进业务结果。

Noul只回答外部明确的是/否问题，不天然表示“没有候选”。需要拒绝选择时，
Choice问题显式提供none_suitable/insufficient_evidence等选项；模型不能自行增加它们。
零候选/单候选优先普通代码处理，不为了展示多轮而调用模型。
每次回环需新候选/新相关事实/可修正反馈；相同提案+依据+反馈摘要不再询问。
