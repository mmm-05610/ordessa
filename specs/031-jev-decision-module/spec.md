# 需求与边界

## 产品定位
主 Agent 承担用户沟通与任务拆分。决策模块对单个任务及当前可见事实进行有限轮判断，返回需要修订、需要澄清、当前阻塞或可交给上层使用的提案。它既不替用户同意风险，也不亲自准备、重配、恢复、占用或调用 Harness。

## 功能需求
| ID | 需求 | 可观察结果 |
| --- | --- | --- |
| R01 | 独立运行 | 无 Ordessa、无 Harness、无真实模型时可运行受控流程 |
| R02 | 外部流程定义 | 替换可信流程代码后判断顺序变化，运行器无需改动 |
| R03 | 任务准入 | 缺目标、边界或验收时返回具名缺口，不悄悄补目标 |
| R04 | 多轮判断 | 新反馈进入下一轮；无新增事实不无限自问直到通过 |
| R05 | 复用优先而非强制复用 | 区分继续原上下文、复用、恢复、等待、调整、新建和不委派 |
| R06 | 动态配置 | 候选描述/外部校验决定可用配置；引擎不硬编码品牌和字段 |
| R07 | 提案非授权 | ready 不启动、不改配置、不写 Profile、不发送任务 |
| R08 | 状态唯一 | 决策记录不是 Agent/Profile/授权/占用权威 |
| R09 | 有限执行 | 轮数、调用次数、时间及输入规模有显式上限 |
| R10 | 失败诚实 | 异常、取消、预算耗尽、观测未知不能变成 ready |
| R11 | 权限与版本 | 精确绑定输入/描述/候选/规则版本；输出不携带秘密或租约 |
| R12 | 可审计 | 可读到每次判断依据、尝试和终态；不自动复发崩溃前调用 |
| R13 | 可替换提供者 | 假 Jev、真实 Jev 和另一个决策提供者遵循同一端口 |
| R14 | 真实接缝 | 使用现有公开服务；缺口具名上报，不读私有属性/数据库补齐 |

## 代表性场景
### 场景 A：用户目标不清楚
WHEN 主 Agent 提交“帮我优化项目”，未给范围和完成条件；
THEN 模块返回 clarify，列出需要用户决定的具体项，不选择 Profile、启动 Agent 或编造验收条件。

### 场景 B：已有单元适用
WHEN 任务边界完整且存在有权限、兼容、可用的既有单元；
THEN 流程可以提出继续/复用，引用准确节点和原生上下文；不能仅凭名称相似判定可继续上下文。

### 场景 C：配置能力新增
WHEN 提供者加入新配置种类及其版本化描述；
THEN 业务流程通过描述和校验服务使用它，运行器及 Jev 网关不增加品牌分支。不能把任意 schema 变成可执行 Python。

### 场景 D：检查后状态变化
WHEN 提案返回后，配置版本、授权、占用或原生运行状态变化；
THEN 消费者重新检查并拒绝过期提案；决策模块不承诺跨外部服务原子性。

## 非目标
本轮不建立公司组织模型、外部 sandbox/worktree 编排、DAG 调度、后台任务队列、自动提案应用、MCP 服务、桌面改版、安装更新机制或所有 Harness 支持。
不把 pydantic-graph 放进 Pacthold；不把 Jev 当聊天模型；不要求主 Agent 每个任务新建工作单元。
可信业务代码可以实现领域规则。运行器只是可复用机制，不能靠“无业务”要求把规则偷偷搬回运行器。
