# 开放式前端环境：状态语义、模型攻击与重构设计

日期：2026-10-03。状态：独立设计任务，未授权生产实现。

## 1. 目标与范围

设计能够承载可插拔 Agent、第三方工具及业务界面的开放前端环境。
重点不是美化 UI，而是澄清状态权威、用户操作、显示投影、插件贡献、原生交互和宿主边界。
先现状盘点和能力边界，再模型设计、多代理攻击、修订复查，最后提交可实施的重构方案。

本任务与 specs/024-open-environment-kernel 后端设计完全分开：只读其公开材料，不写该目录，不代其做裁决。
两侧尚未稳定的契约记入接口问题清单，不为等待后端结果阻塞所有前端设计，也不假设候选契约已实现。

唯一写入范围：specs/025-open-frontend-environment/**。
可写设计文档、离线状态模型和隔离的 UI 验证材料；源码及其他规格只读。
不改变生产代码、数据、登录、凭证、应用状态；不操作真实窗口、不启停用户服务、不调用真实模型。
不安装新依赖、不联网下载第三方实现、不新建 worktree、不切分支、不提交/合并/推送。
不修改 AGENTS.md，不更新云端网站。需要真实交互、联网调研或扩大写权时另行提出。

## 2. 已确定的产品原则

1. 前端是开放工作环境，不是已知品牌能力的功能菜单集合。插件可贡献界面和原生交互形态。
2. 原生能力通过已有可承载入口新增时，不要求核心增加专用接口或命令枚举。
3. 插件可装入、停用、移除；无 Chat、Profile 或某品牌 Harness 时基础环境仍然可用。
4. Profile 是可选的配置清单，不是所有会话配置的必需中心。
5. 模型切换只覆盖模型相关字段；Profile 切换只覆盖其实际包含的字段；重叠字段按用户操作顺序覆盖。
6. Profile 未包含 model 时不能清掉现有 model；包含 model 时，模型展示要跟随统一配置状态变化。
7. 输出中修改配置不打断当前 Agent，按既定发送边界生效；不为此制造复杂的强制确认 UI。
8. 重新选择同一 Profile 是新的应用操作，不因值相同而忽略；不恢复独立“重新应用”按钮。
9. 同一事实只有一个权威；控件、转换器和插件投影不能各自维护不同的“当前实际配置”。
10. 前端不处理 Harness 内部差异；品牌适配归 Harness。前端通过领域公共契约交互，不写品牌分支。

此前“前端7包”等仅是候选组织方式，不能硬编码成设计前提。先定语义和边界，再确定包数与目录。

## 3. 核心反例与单一状态权威要求

曾出现：选择 Profile 并发送成功后，模型控件仍显示空/旧值；随后选择模型，显示、实际配置和发送链不一致。
用户指出：实际状态和操作、显示应分离，实际状态只有一份。该现象是调查入口，不预先断言某两个文件是根因。

必须设计以下四类信息如何关联、谁拥有、何时变化：
- 已确认事实：后端/原生参与者实际确认了什么；未知不等于未设置。
- 用户操作：有身份、顺序及作用域的变更意图，不是下拉框值本身。
- 待应用配置：从基底与操作得到的统一解析结果，不是控件各自拼出来的副本。
- 展示与草稿：展示是投影；输入文本和未保存表单属于独立草稿，不代表已应用事实。

“只有一份状态”不是把所有信息塞进单个全局 store，也不是把期望值伪装成已确认事实。
允许不同领域、会话、窗口拥有不同状态，但每种事实必须列出唯一所有者及唯一更新入口。
派生状态可以缓存，必须说明来源版本、失效条件和重建方式，不能反向成为第二个权威。
协议/数据转换器可转换和校验形状；如果持有必要传输状态，必须证明它不重复管理领域事实。

## 5. 前端环境能力边界草案

- 一个插件运行与贡献撤销机制：发现、依赖、激活、作用域、卸载；不在 Workbench 再建插件加载器。
- 一个界面组织机制：导航、页面、面板、设置、弹层、命令位置、输入入口；业务内容归插件。
- 一套可观察领域状态接入契约：允许多个领域所有者，不由核心储存所有业务对象。
- 一套操作路由及结果关联机制：身份、作用域、顺序、版本/代际，区分成功、拒绝、未知和待确认。
- 可插拔交互承载：消息、命令、流、终端或第三方视图，不假设所有参与者只有聊天文本界面。
- 原生能力透传和可选富展示：未知命令不误拦截，未知事件不擅自解释，缺展示器时明确降级。
- 多会话/实例/窗口隔离，历史读入与运行事实关联，断连/恢复时不伪造状态。
- 安全的原生桥及第三方内容承载；HTML/链接/事件不能获得任意脚本或系统能力。
- 生命周期、背压、订阅清理、焦点及输入稳定；不能用全局刷新破坏输入或重新提交副作用。

非目标：重做 Harness 内部状态机、用前端维护后端执行账、引入必需 Profile、全局万能 store、
新 Agent 协作业务、终端/第三方工具内部功能重写、全产品视觉改版或生产实现。
终端与嵌入视图是待检验的承载形态，不意味着本轮已批准执行任意代码或完全信任插件。

## 6. 每版模型必须解释

1. 插件、界面贡献、领域状态所有者和运行实例分别是什么；谁提供通用机制，谁拥有业务。
2. 用户命令如何到达领域所有者；状态如何单向投影到多个控件；不存在控件之间互相同步“实际状态”。
3. 后端已确认事实、前端意图及待生效配置怎样区分；哪条信息有资格决定模型标签和发送参数。
4. 不完整 Profile、同值重选、快速交替操作、输出中切换、原生自主变更分别如何合并。
5. 请求回执、原生观察和本地意图冲突/乱序时怎么核对；不把晚到回执覆盖更晚的用户操作。
6. 状态持久化与重启恢复分别负责什么；失败草稿、未知结果不得被自动重发。
7. 草稿会话和原生会话如何关联，不因切换控件就创建空原生会话。
8. 插件移除、热更新、旧回调、旧 Token、陈旧选择项和订阅怎样失效。
9. 原生命令与环境命令冲突如何处理，不能把未知 /workflow 当成环境未注册命令而拒绝。
10. main/preload/renderer 与普通网页的能力边界；插件身份不等于无限系统授权。
11. 可替换组件、设置项和页面如何共享业务状态，而不重复实例化业务所有者。
12. 一套清晰公共 API 如何让完整业务插件装入，不需要它理解宿主或其他插件的内部实现。

每版提供中文定义、状态/操作时序图、合法与非法序列，以及至少三个完整接入例子。
不先选状态库，不把 React hook、Redux/Zustand 或新抽象名称当作语义答案。

## 7. 独立多代理攻击与迭代

沿用本轮模型审查方式：主会话唯一写模型和进度，最多3个攻击子代理并行，无嵌套代理。
本任务与后端代理组独立；不主动向后端会话发消息，不干扰其工作。接口分歧在本目录记问题清单。
子代理只读代码/设计快照，返回攻击报告，不写生产代码、不做 Git 写操作。
每次提供自包含版本、边界、任务和返回格式，不依赖整段历史。

- A 状态语义：重复权威、覆盖顺序、乱序回执、会话隔离、草稿/事实混同、缓存失效。
- B 开放性与生命周期：新插件完整装入、原生未知能力、卸载/升级、贡献撤销、缺可选插件。
- C 交互与安全：焦点/IME、重渲染、弹层、并发输入、流与背压、第三方内容、IPC 边界。

每个攻击必须给出：编号、版本、前置条件、事件序列、破坏的不变量、预期结果、严重度与建议。
至少 V1→三路攻击→V2→再攻击；最终另有未参与模型编写的独立复查。
逐条保留处置和复查证据，不覆盖历史问题，不用“已考虑”或代理好评替代验证。
连续两轮同一重大矛盾未解决时向用户提出选项，不无限烧额度，也不把问题移出范围假装通过。

## 8. 必须覆盖的场景

每组需要预期结果、正反例、缺能力时行为和离线验证/未来产品验证方法：
1. 无 Chat/无 Profile/无特定 Harness 时环境可启动，基础界面不依赖业务插件。
2. Profile 含模型：模型标签与统一待应用状态一致；回执前不能冒充已确认。
3. Profile 不含模型：保留现有模型；model 单项操作不清掉提示词/Skill 等无关配置。
4. 先Profile A再model B与反向顺序；按字段覆盖，而非整体重置临时配置。
5. 重选同一个 Profile 是新操作；React同值优化或原生select限制不吞操作。
6. Agent输出时改配置不打断；下一次提交使用一致快照，不混用两份转换结果。
7. 打字及中文IME组合期间收到状态/流更新，焦点、光标、草稿和错误提示不闪烁重置。
8. 发送成功清草稿，明确拒绝保留草稿，结果未知不自动重发；错误有真实关联和稳定生命周期。
9. 新草稿选择模型/Profile不创建空原生会话；首次发送建立关联后状态不丢。
10. 快速切会话时旧请求返回，不覆盖新会话；两个会话同模型也不能共享可变实例配置。
11. 断连重连/冷启动，历史与已确认配置可核对；旧运行身份不冒认新owner/generation。
12. 原生参与者在自身入口改变配置，环境通过证据更新展示，不被本地旧选择覆盖。
13. 上游新增未知 /workflow 可通过已承载原生入口使用，缺原生通道时明确限制。
14. 环境命令与原生命令重名，路由规则可预测且能显式使用原生入口。
15. 未知事件、工具内容、结构化输出展示降级；禁止注入脚本/伪造审批。
16. 新插件贡献页面、侧栏、设置、菜单、输入入口和领域服务，不改核心品牌分支。
17. 插件卸载撤销贡献/订阅；正在打开的页面/弹层与未完成操作按明确规则处理。
18. 重新启用/升级时旧回调和Token不会误操作新实例；不同构建消费同一契约身份。
19. 多个视图展示同一领域事实，不创建多份业务状态；视图关闭不销毁仍被使用的业务对象。
20. 菜单不被overflow裁剪，设置可关闭，Esc/焦点返回有效，系统窗口按钮不被遮挡。
21. 高频事件、长列表、无限流和断开的订阅有边界；不因无限保留数据而内存增长。
22. native/main/preload/renderer 边界不允许未授权插件加载路径、调用或内容穿透。

至少三个完整例子：原生Agent交互插件；资源管理插件（含页面/设置/Chat贡献）；非聊天工具（终端或独立视图）。
另给 Profile/model 配置链的端到端状态轨迹，说明每一步谁拥有事实、谁只派生展示。

## 9. 重构方案要求

模型收敛后给 packages/frontend 子包划分及 apps/desktop、plugins、products 的职责。
每包写公共入口、允许依赖、禁止依赖、状态所有权及独立验证方法，不机械对称后端。
现有loader/host、workbench、foundation、ui/ui-components、connections、bridges逐项映射：保留/合并/拆分/退役。
通用机制优先复用现有实现；领域状态重复处逐项标出，不只用新store包裹旧状态。
列出共享契约、扩展ID、Token单实例、构建装配、持久化格式及旧入口的兼容处理。
每阶段有行为不变量、定向正反例、回归范围、失败/缺席行为、回滚点；代码迁移与行为变更分开。
不得把协议/配置语义变化伪装成内部重构；后端所需契约变化仅列问题，不自行修改或冻结。
