# Capability gaps and execution boundary

This directory specifies the complete GitLab Product Development Flow as an external process and supplies a report schema/template. It has no compilable full-flow manifest. The isolated `projection/method.yaml` is explicitly named `ordessa.gitlab-product-change.report-smoke` and declares `full_flow_support: unsupported`; it binds one real artifact-capture operation only. There is no evidence here of a published method or runtime execution.

| Capability | State | Concrete boundary / reference |
| --- | --- | --- |
| Method manifest/resource validation and exact method-bound `MethodPayload` schema binding | Supported by the current compiler and Engineering artifact path | `packages/engineering/src/ordessa_engineering/methods/definitions/schemas/v1.py`; `application/usecases/material_closure.py::verify_material` and `_verify_method_content`; `application/orchestration/method_content.py::document_spec` and `validate_document_content`. This package declares the report schema `$id` and binds a `MethodRef`; the coordinator must verify the actual release payload. |
| Decimal metric representation in schema-bound report values | Ordessa report design accepts JSON integers, strings, or null; encode decimal values as exact decimal strings (for example `"0.70"`) | This accommodates the canonical JSON body profile used by `MethodContent.from_value`; JSON floating-point values are rejected by `packages/infrastructure/src/ordessa_infrastructure/encoding/canonical_json.py`. This is an Ordessa payload constraint, not a GitLab Product Development Flow requirement. |
| One report Artifact creation through a registered operation | Supported only by the isolated smoke projection | `engineering.artifacts.create`, interface v2 and the exact digest declared in `projection/method.yaml`; `application/usecases/artifacts.py::ArtifactUseCases.create`. Its `completed` outcome means the Artifact transaction completed, not that GitLab accepted the report or any flow stage. |
| Input mapping to the operation's `kind`, `initial`, and `method_refs` | Supported by slot mapping, with caller-supplied values | `application/orchestration/method_bridge.py::MethodBridge.operation_inputs`; the graph maps `artifact_kind`, `initial_payload`, and `method_refs`. The workflow has no literal/config-to-input binding or input-value schema enforcement. |
| Current Workguard/CAS and conditional implementation mechanisms | Implemented in parts; production source/catalog binding and complete assembly remain unfinished | Current Engineering capability inventory: `docs/implementation/packages-convergence-20261012/engineering/CAPABILITIES.json`; expression details: `METHOD-EXPRESSION.md`. Those general mechanisms are not GitLab event identities or a complete GitLab adapter, and this package does not claim to use them to drive the flow. |
| GitLab event identity and trusted deployment/current-state source | Missing | No registered GitLab event source, authenticated GitLab identity binding, deployment source, or target-instance observation descriptor is declared in the cited capability inventory. Reports are external assertions with references; Ordessa does not fetch/verify target state. |
| Generic conditionals, loops, parallel execution, or full lifecycle routing | Missing from `ordessa.methods/v1` | `packages/engineering/src/ordessa_engineering/methods/definitions/schemas/v1.py` defines the current workflow expression; `methods/validation/workflow.py` validates its acyclic graph. It has no general conditional/loop/parallel construct. This package uses one capture operation only. |
| Published wait descriptors and production wait source | Missing | The current `CAPABILITIES.json` reports `published_wait_descriptors` as empty. `wait_kinds: []` in this package is intentional. Block, resume, and recheck are specified for external actors and recorded in reports. |
| Git, CI, MR review, deployment, metrics observation, or product-acceptance decision | Outside this method's execution boundary | These are performed by GitLab, external systems, and authorized people. Report fields preserve their cited claims and decisions; no operation in this manifest performs them. |
| Validation/build parallel tracks, stage skipping, rework, postponement, cancellation, and subsequent iteration | Specified in `PROCESS.md` and represented by the report contract; not routed by the graph | The schema captures status, rationale, owner, links, blocker/rework history, deployment/version evidence, outcomes, and closure. Each later report is a new external capture; there is no engine wait/resume or automatic iteration. |
| Method publication and runtime execution proof | Not established | No published-catalog registration, engine run, or production activation evidence is included. `_support/design-traces/` contains synthetic report examples only. |

The package must not be described as an executable GitLab lifecycle or as a verified integration. Do not create fake operation IDs, fixture catalogs, or acceptance switches to fill these gaps. A future adapter would require separately registered and authenticated GitLab event/current-state sources, explicit contracts for deployment and measurement evidence, and a richer routing expression before the complete process could be driven by Ordessa.
